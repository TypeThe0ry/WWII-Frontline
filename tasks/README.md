# 任务体系说明（tasks/README.md）

> 读者：逐任务执行的 Sonnet（以及审阅它的 Fable / 人类负责人）。**每次会话开始时先读本文、`docs/ARCHITECTURE.md`、`tasks/STATUS.md`。**
> 本文是执行规则的摘要，不替代 `docs/ARCHITECTURE.md` 等约束性文档；冲突时以 `docs/` 为准，且按 §5.1 处理。
> 章节编号稳定，其它文档按 "tasks/README.md §n" 引用，不得重排。

---

## 1. 体系概览

| 文件 | 作用 | 谁改 |
|---|---|---|
| `docs/MILESTONES.md` | 里程碑目标、退出标准、演示脚本、素材/人工/对标批次、风险、Fable 审阅检查点 | Fable |
| `tasks/INDEX.md` | **全部任务的唯一清单**：ID、slug、工作流、依赖、规模、引用章节、范围、验收指标、素材需求 | Fable（执行者仅在 §5.6 续作时追加） |
| `tasks/STATUS.md` | 每个任务的状态、**实测结果**、遗留问题、完成提交；顶部"当前里程碑/下一个任务/blocked 清单" | 执行者每次会话更新；Fable 在检查点推进里程碑 |
| `tasks/M{n}-{三位序号}-{slug}.md` | 单个任务的详细说明（模板见 §2.2） | 展开时由执行者创建（§2.1） |
| `docs/PLAN_ISSUES.md` | 执行中发现的计划/架构/数值问题（执行者**只写这里，不改架构**） | 执行者新增条目；Fable 裁决 |
| `LICENSES.md` | 素材准入台账；只有状态 `OK` 的素材可进入构建 | 人类负责人登记；执行者只读（及校验） |

任务编号 `M{n}-{三位序号}`，**编号即执行顺序**：同一里程碑内被依赖者编号必然小于依赖者。工作流（stream）与缩写见 `tasks/INDEX.md` §0。

## 2. 任务文件

### 2.1 任务文件的展开（step 0）

规划阶段只产出了 INDEX 行，**任务文件按需展开**：执行者领取任务后，若 `tasks/M{n}-{三位序号}-{slug}.md` 不存在，先按 §2.2 模板由 INDEX 行 + 其"引用章节"所指的文档段落**展开任务文件**（把"一句话范围"展开成具体文件路径、接口、行为；把"关键验收指标"展开成编号验收清单），作为该任务提交的第一个 commit。展开时：

- 先**精读引用的文档章节**；只复述文档已有的内容，不自行发明接口或数值；缺失的内容写 `docs/PLAN_ISSUES.md`，不要擅自拍板。
- 展开后若发现任务明显超过一次会话（规模 > L），按 §5.6 处理，**不要硬做**。
- 任务文件一经展开即视为合同：后续改动须在"备注"里记录变更与原因。

### 2.2 任务文件模板

固定小节，**顺序与标题不得改动**（便于脚本与审阅检查）：

```markdown
# {ID} {标题}

## 元数据
- 里程碑：M{n}
- 工作流：{stream}
- 规模：S | M | L
- 依赖：{任务 ID 列表，或"无"}
- 素材需求：{需求 ID 前缀，或"无（灰盒即可）"}；素材状态：{real / placeholder / n.a.}
- 引用文档：{如 ARCHITECTURE §6.4; GAMEDESIGN §9.1}

## 背景
{为什么做这个任务；它在里程碑中的位置；上游产出了什么、下游会用它做什么。
 逐条引用文档章节（ARCHITECTURE.md §x.y），并摘出执行所需的关键约束与数字，使读者不必先读全文。}

## 具体内容
### 要创建/修改的文件
- `path/to/file.rs` —— {职责}
- `path/to/other.ts` —— {职责}
### 要实现的行为
1. {行为 1，含输入/输出/边界条件}
2. ...
### 接口与数据
- {公开接口签名草案 / 数据 schema / 消息字段；引用 ARCHITECTURE §8 的已有定义，不得与之冲突}

## 不做什么
- {明确排除的相邻功能，指向负责它的任务 ID}

## 验收标准
1. {可测试的条目：带数字阈值 + 测量方法（命令/脚本/测试名）}
2. ...
（每条独立可判；禁止"性能良好""基本可用"之类表述）

## 测试要求
- 单元测试：{范围与最低覆盖：必测的边界/错误路径}
- 集成/无头测试：{headless-client / 脚本化场景 / netem 条件}
- 性能基准：{criterion / 帧时间采集 / 压测，及基线文件位置}
- 回归：{需要更新的快照/视觉基线/确定性哈希}

## 性能预算
- {引用 ARCHITECTURE 的预算数字：ms/tick、ms/帧、kbps、MB、draw call 等；
  若本任务无新增预算，写"不得使 §x 的既有预算回归"并给出回归检测方式}

## 完成定义
- [ ] 全部验收标准有实测数字，已写入 `tasks/STATUS.md`
- [ ] 测试通过（`cargo test` / `vitest` / CI 作业名）；`cargo clippy -D warnings`、`eslint`、`tsc --noEmit` 干净
- [ ] 性能预算已测（或明确标注"参考机不可用，partial"）
- [ ] 无新增禁用依赖（ARCHITECTURE §4.5）；`/data` 校验通过
- [ ] 占位素材已按 ASSET_GAPS §3 命名（`PH_{需求ID}`）；缺失素材需求 ID 已在回报中列出
- [ ] 文档同步：若任务产生了接口/数据变更，已更新对应 docs 的"变更说明"并在 PLAN_ISSUES 登记（不改章节编号）
- [ ] `tasks/STATUS.md` 对应行与顶部摘要已更新；提交信息含任务 ID

## 备注/已知风险
- {风险、未验证假设、后续任务需要注意的事项、PLAN_ISSUES 条目编号}
```

### 2.3 验收标准的写法要求

- 每条都要有**数字阈值**和**测量方法**，例如："`cargo bench -p sim kcc_step` 单次中位数 ≤ 20 µs（参考机）"；"`test-loadtest-20` 30 min：`tick_ms` P99 ≤ 28 ms（`/metrics` 直方图）"。
- 引用 ARCHITECTURE 的预算数字时写明章节（如 §6.10）。**不得自行放宽数字**；若认为数字不合理，按 §5.1 写 PLAN_ISSUES。
- 需要人类/硬件/录像才能测的条目：标注"需人工/参考机"，缺失时该条记 `未测`，任务状态至多为 `partial`（§4）。

## 3. 一次会话的标准流程

1. 读本文、`docs/ARCHITECTURE.md`、`tasks/STATUS.md`；按 §7 选定任务。
2. 若任务文件不存在 → §2.1 展开并提交。精读"引用文档"所列章节与"依赖"任务的产出。
3. 把 STATUS 中该任务置 `in-progress`（提交或在最终提交中体现）。
4. 实现；**测试先行或同步**（先写会失败的验收测试，再实现）。
5. 跑全部验收与测试，记录实测数字（保留命令与输出路径）。
6. 更新 `tasks/STATUS.md`（状态、实测结果、遗留问题、提交哈希）与顶部摘要；有问题则写 `docs/PLAN_ISSUES.md`。
7. 提交（信息以任务 ID 开头，如 `M0-012: sim weapon rifle`）；最终回报：做了什么、实测数字、遗留问题、缺失素材需求 ID。

**一次会话只做一个任务**（S 级相邻且同工作流、依赖满足的任务可合并，但每个任务各自更新 STATUS 与提交）。

## 4. 状态枚举

| 状态 | 含义 | 何时使用 |
|---|---|---|
| `todo` | 未开始 | 初始状态 |
| `in-progress` | 进行中 | 已领取且本会话未做完；下次会话**优先续做** |
| `done` | 完成 | **全部**验收标准有实测数字且达标；完成定义全部勾选 |
| `partial` | 部分完成 | 核心已完成，但有验收项因客观原因未达标/未测（缺参考机、缺录像、素材只有占位、预算未达标待裁决）；**必须**在"遗留问题"写明缺什么、对应 PLAN_ISSUES 编号 |
| `blocked` | 被阻塞 | 缺人类输入/素材（`LICENSES.md` 非 OK）/外部条件；**必须**在顶部"blocked 清单"登记"所缺条目、日期、谁来解除" |

规则：

- 依赖是否满足：依赖任务为 `done` 即满足；为 `partial` 时由执行者判断其遗留项是否影响本任务，**写入本任务备注**；影响则视为不满足并跳过。
- `done` 不得带"待测"项；有则改 `partial`。**不要为了推进而把 partial 写成 done。**
- `blocked` 只用于"自己无法解除"的情形；技术难题先在 PLAN_ISSUES 写方案，不要标 blocked 后放弃。
- 里程碑验收任务（`m{n}-acceptance`）为 `done` 的条件：MILESTONES 对应退出标准每项都有实测数字，或已逐项登记为 `partial` 原因并经 Fable 同意。

## 5. 执行规则摘要

### 5.1 不改架构

- `docs/ARCHITECTURE.md`、`GAMEDESIGN.md`、`UI_SPEC.md`、`MAPS.md`、`REFERENCE_MEASUREMENTS.md` 及总控裁定（R1–R11）是**约束**。执行者**不改这些文档的结论、接口、预算、章节编号**。
- 发现文档冲突/错误/做不到时：写 `docs/PLAN_ISSUES.md` 条目（问题、证据、建议方案、受影响任务），在任务备注引用，**按文档继续做能做的部分**；不能继续则任务标 `partial`/`blocked`。
- 唯一例外：接口落地时必须补全的**细节**（如字段位宽的具体取值）可写入任务文件与代码注释，并在 PLAN_ISSUES 记一条"细化"，由 Fable 在检查点回写文档。

### 5.2 素材

- **只使用 `LICENSES.md` 中已登记且状态为 `OK` 的素材**；`PENDING`/`REJECTED`/未登记一律不得进入主分支、不得处理、不得上传。素材管线（`asset-pipeline-ingest-gate`，M1）会机械拒绝。
- 禁止自行从非正规渠道下载素材、禁止自制模型/贴图/音效、禁止 AI 生成素材（A2、D-MOD）。UI 图标/字形由执行者按 UI_SPEC 以 SVG/Canvas 原创绘制（待人类确认，见 NEEDS_HUMAN）。
- 处理后素材只以 `.fpak` 容器分块形式交付（D-PAK、R11）；不提交 `assets/incoming/` 与 `assets/processed/`。
- 字体、OSM 衍生层等也属"素材"，同样走台账与署名。

### 5.3 灰盒占位约定（`docs/ASSET_GAPS.md` §3 的摘要）

- 素材没到位**不是阻塞理由**：用程序化灰盒（盒/圆柱/胶囊/球）占位，**尺寸与碰撞取自 `/data`**，保留真素材将使用的挂点（socket）。
- 命名：材质 `PH_{需求ID}`，节点 `PH_{需求ID}__{实例名}`；阵营着色（美军橄榄绿、德军灰，仅调试配色）；开发构建显示需求 ID 标签。
- 音频缺失：返回短静音 `AudioBuffer`，每个缺失需求 ID 每会话只打一条日志；**不用其它层顶替**，不放提示音。
- 素材管线输出"缺失素材报告"（real/placeholder/missing），manifest 带 `placeholder` 字段。
- 只有名为 `assets-m*-integrate-*` 的任务真正依赖素材；素材未 `OK` 时该任务标 `blocked`/`partial`，**不影响其它任务**。

### 5.4 服务器权威与确定性

- 一切影响胜负的状态由服务器裁决；客户端只上报输入（P1）。规则只在 `crates/sim`，**不得在 `server` 内实现游戏规则**（ARCHITECTURE §4.3.4）。
- `sim` 禁用：墙钟、`thread_rng`、`HashMap/HashSet`（用 `indexmap`/`BTreeMap`）、多线程、I/O、`wasm-bindgen`（§4.3.2）。随机数用 `Pcg64Mcg` 与规定的种子公式。
- 预测与对账**不要求 WASM 与原生逐比特一致**（R5）：只在 native/native、wasm/wasm 之间做阻断性哈希比较；跨平台仅信息性。
- 敌方信息下发遵守 R3；Garrison 放置者遵守 R1；资源与 Supplies 分离遵守 R6；火炮遵守 R7。**任务文件与代码必须以 §3c 裁定为准**，遇到文档中与之冲突的旧表述，按裁定实现并在 PLAN_ISSUES 记一条。
- 游戏性数值只在 `/data`；初值状态 `initial`，经史实复核/对标测量后改为 `reviewed`/`measured`；**客户端不硬编码数值**（ARCHITECTURE §4.4）。

### 5.5 性能预算是验收的一部分

- ARCHITECTURE 的预算（§6.9 带宽、§6.10 服务器 CPU、§11.4 体积、§13 画质/帧/内存、§16.5 bot）**是验收标准，不是愿望**。任务有相关预算则必须测并写入 STATUS；超预算 = 缺陷，状态至多 `partial`，并写 PLAN_ISSUES。
- 基准必须可重复：固定种子、固定机位、固定参考机；记录机器型号与命令。
- 没有参考机/硬件时：标 `未测`，不要用别的机器的数字顶替后标 `done`。

### 5.6 任务过大与续作

- 任务超出一次会话（规模 L 的上限 ≈ 600 行新代码或等量工作）时：**停在可提交的稳定点**，状态 `partial`，在 PLAN_ISSUES 写拆分建议。
- 允许的最小改动：在 INDEX/STATUS 中紧跟原任务**追加续作任务 `M{n}-{NNN}b`**（`c`、`d` 依次类推），继承原任务的引用章节，范围写"续 M{n}-{NNN}：{剩余内容}"；原任务的下游依赖改为同时依赖续作任务。**不得重新编号既有任务**。
- 其它对 INDEX 的改动（新增独立任务、改依赖、改规模）只能由 Fable 做；执行者写 PLAN_ISSUES。

### 5.7 知识产权与对外名称

- 参考作品只能黑盒观测；禁止拆包/解包/协议解析/素材提取；游戏内、UI、文档、提交信息、公开材料中不得出现参考作品名称/商标/截图。
- 统一原创命名（BRIEF §1.5 / ARCHITECTURE §1.5）：模式 Frontline/Assault/Skirmish；重生点 Garrison/Outpost/Airhead/Observation Post (OP)；资源 Manpower/Munitions/Fuel；能力 Supply Drop/Ammo Drop/Bombing Run/Strafing Run/Precision Strike/Recon Flight/Rally/Airhead；兵种名见 GAMEDESIGN §5.1。
- 数值第一来源是真实史料；游戏性数值标"初值 + 待调参"，对标来源是 `docs/REFERENCE_MEASUREMENTS.md` 的黑盒测量（录像与原始数据**不入库**）。

### 5.8 代码质量底线

- 不写与任务无关的重构；不留 `TODO` 而无 PLAN_ISSUES 编号；不引入 INDEX/ARCH 未列出的新运行期依赖（如确需，写 PLAN_ISSUES 并先 `cargo deny` / `npm audit`）。
- 解码路径禁用 `unsafe`；所有网络输入做长度/范围检查（ARCHITECTURE §19.1）。
- UI 文案一律走 i18n key（A7）；用户内容不得 `innerHTML` 注入。
- 提交粒度：每个任务至少一个提交；提交信息以任务 ID 开头，正文写验收数字摘要。

## 6. blocked 与人类输入

- INDEX §7 列出所有范围以 `[人工…]` 开头的任务（录像、DEM 下载、史料校对、账号/域名/主机、法务、测试者招募、参考硬件等）；§8 列出真正依赖素材的接入任务。
- 缺人类输入时：①把该任务置 `blocked`；②在 STATUS 顶部"blocked 清单"写"所缺条目 — 日期 — 谁来解除"；③在 `docs/NEEDS_HUMAN.md`（人类待办清单，总控维护）末尾追加条目（只追加，不改他人条目）；条目写明任务 ID 与所缺输入；④**继续做下一个依赖已满足的任务**，不要空等。
- 人类提供输入后，由人类或 Fable 把任务改回 `todo`/`in-progress`；执行者不得自行假设输入已到位。
- 不得编造数据来弥补缺口（DEM、录像测量值、史料数值、素材许可证状态）。无法联网核实的事实写"未核实"。

## 7. 如何选下一个任务

按顺序判断，选出第一个满足的：

1. STATUS 中**有 `in-progress` 任务** → 续做它（编号最小者）。
2. 取 `tasks/STATUS.md` 顶部的"当前里程碑" `M{n}`。**只能从 `M{n}` 中选**（`M{n+1}` 要等 Fable 审阅后推进"当前里程碑"；不依赖审阅且 INDEX 已标注的人工/采购事项除外）。
3. 在 `M{n}` 的 `todo` 任务中，找出**所有依赖都已满足**的（§4：依赖 `done`；`partial` 依赖按备注判断）；
4. 在其中选**编号最小**者。
5. 若没有候选：
   - 若剩余任务全部被 `blocked` 或依赖未满足 → 在 STATUS 顶部"下一个任务"写"无（等待：…）"，列出阻塞原因，回报并结束会话；
   - 若本里程碑任务已全部 `done`/`partial` 且 `m{n}-acceptance` 已完成 → 回报"等待 Fable 审阅检查点"，结束。
6. 选定后在 STATUS 顶部"下一个任务"写入后继候选（可选），并开始 §3 流程。

**不要**跳过编号去做"更有趣"的任务；**不要**为了避开难任务而选依赖未满足的任务。素材未到位不是跳过理由（§5.3）。

## 8. STATUS 与 PLAN_ISSUES 更新规范

- `tasks/STATUS.md`：
  - "实测结果"列写数字与测量方式（如 `tick_ms P99=21.4 ms；100×30 min；报告 reports/m2-load.json`），不能只写"通过"；
  - "遗留问题"列写 PLAN_ISSUES 编号（如 `PI-012`）；
  - "完成提交"列写 commit 短哈希；
  - 顶部三项摘要（当前里程碑 / 下一个任务 / blocked 清单）每次会话结束前必须与表一致。
- `docs/PLAN_ISSUES.md`：条目模板见该文件；执行者新增条目，**不得删除或改写他人条目**；状态由 Fable 改。
- 报告产物（压测/性能/平衡）放 `reports/`（不含录像与素材原件）；大文件不入库，只存摘要与哈希。

## 9. 速查：每个里程碑的最后一个任务

`m0-acceptance` … `m4-acceptance`（INDEX 中各里程碑最后一行）。它们不写功能代码：逐条核对 `docs/MILESTONES.md` 的退出标准、走演示脚本、汇总 STATUS、整理 PLAN_ISSUES，为 Fable 的审阅检查点准备材料。
