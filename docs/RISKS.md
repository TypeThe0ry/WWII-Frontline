## 0. 使用说明与评分口径

### 0.1 重要声明（诚实）

1. **本文不是法律意见。** §5 的法律/IP 风险是项目经理视角的风险识别与降低手段清单；其中涉及版权（选择与编排）、商业外观、不正当竞争、德国等司法辖区的符号限制、GDPR、年龄分级的结论**全部未经律师核实**。凡金额或后果较大者（尤其 R-31、R-33、R-39），**建议在 M0 结束前由人工咨询有资质的律师**（NEEDS_HUMAN H-010、H-040）。
2. 本文的概率、影响是**项目经理的判断估计**，不是统计结论；M0 后应用实测数据重估。
3. 引用的浏览器支持现状、价格、许可证条款，均沿用其它文档已有的核实记录（核实日期 2026-11-17），本文**不新增**外部事实；凡原文标"未核实"的，本文同样标"未核实"。
4. 估算（如 LLM 费用上限、带宽）若出现，均标【估算】并给出算式，可复核。

### 0.2 评分与图例

| 项 | 取值与含义 |
|---|---|
| 概率 | **高**：在当前计划下，更可能发生而不是不发生（> 50%）；**中**：20–50%；**低**：< 20%。 |
| 影响 | **高**：导致里程碑延期 ≥ 1 个月、需更改架构/范围/素材路线，或有下架/法律后果；**中**：延期数周或明显降级体验；**低**：局部返工、可在一个任务内消化。 |
| 得分 | 高=3、中=2、低=1，概率×影响（1–9）。≥ 6 为"红"，4 为"黄"，≤ 3 为"绿"。 |
| 负责方 | **人** = 人类负责人（决定/付款/注册/法务/录制/运维）；**执行者** = AI 执行者（Sonnet，写代码、写脚本、做测量分析）；**Fable 审阅** = 里程碑末的独立审阅（核对验收证据、更新本表）。多方时第一个为主责。 |
| 最晚验证里程碑 | 该风险**最迟必须被验证（证实/证伪/已降到可接受）**的里程碑；超过则视为计划事故。M0 = 技术验证，M1 = 垂直切片，M2 = 完整 Frontline，M3 = 全兵种全载具，M4 = Omaha/Foy/公开测试，"上线前" = 公开测试开始前。 |

### 0.3 每条风险的固定字段

类别｜概率｜影响｜最晚验证里程碑｜负责方｜**描述**｜**触发信号 / 早期发现**｜**缓解方案**（具体到任务或设计决定）｜**应急预案**（成真后怎么办 / 降级方案）。

### 0.4 维护规则

- 每个里程碑末，Fable 审阅同时更新：①每条风险的概率/影响是否变化；②"最晚验证里程碑"是否被满足；③新增风险（见 §9）。
- "触发信号"必须尽量是**可度量的**（毫秒、MB、kbps、日期）；一旦信号出现，执行者在任务回报里**显式写出风险 ID**，由人决定是否启动应急预案。
- 应急预案一经启动，必须在 `docs/ARCHITECTURE.md` §20 或对应文档里回写"已降级"记录，禁止只在聊天里决定。

## 2. 技术风险

### R-01 WebGPU 兼容性与驱动差异

类别：技术｜概率：中｜影响：中｜最晚验证：M0｜负责方：执行者（主）、人（提供测试设备）

- **描述**：ARCHITECTURE §5.0 的核实记录显示 WebGPU 在桌面 Chrome/Edge 稳定，Firefox 版本互相矛盾（**未核实**），Safari 26 起；Linux、旧驱动、企业策略下仍可能缺失。已启用 WebGPU 的机器上还可能遇到驱动 bug（纹理格式、compute 同步、`maxStorageBufferBindingSize` 等 limit 偏小、设备丢失 `device.lost`）。A4 把 Chrome/Edge 定为一等公民，所以这条主要威胁 Firefox/Safari/老卡用户。
- **触发信号**：M0 在测试设备矩阵（H-021）上有任一设备 `requestAdapter()` 为空、`device.lost` 事件、compute pass 结果与 CPU 参考不一致、同一场景视觉回归帧差超过阈值。
- **缓解方案**：
  1. M0 任务 `engine-probe`：启动页能力探测（adapter limits、`adapter.info`、texture-compression-bc/astc/etc2 特性、timestamp-query），把结果写入匿名遥测字段（ARCHITECTURE §18.3 的客户端遥测，默认关闭/需同意）。
  2. 所有 compute 效果（Hi-Z、froxel、TAAU、直方图）必须有**CPU/片元参考实现或降级开关**（ARCHITECTURE §10.3 已列）；compute 结果加单元级"金标准对比"测试（固定输入、容差）。
  3. 处理 `device.lost`：自动重建引擎并回到部署界面，不得白屏；有"强制使用 WebGL2"的设置项和 URL 参数 `?gpu=gl`。
  4. 建立**已知问题表** `docs/KNOWN_GPU_ISSUES.md`（驱动版本 + 症状 + 规避），由执行者在每次发现时追加。
- **应急预案**：某 GPU/驱动组合出现不可规避缺陷 → 在能力探测里加黑名单，强制 WebGL2；Firefox/Safari 若 WebGPU 路径不稳，则在这两类浏览器上默认 WebGL2 并在设置里标"实验性 WebGPU"。
- **对应文档**：ARCHITECTURE §5.0、§10.3、§13.6、§20 #6。

### R-02 WebGL2 兜底的画质/性能落差

类别：技术｜概率：高｜影响：中｜最晚验证：M0｜负责方：执行者

- **描述**：WebGL2 路径无 compute：无 Hi-Z 遮挡剔除、无 froxel 体积雾、TAAU 退化为 FSR1 式空间放大、AO 降级、无 SSR、阴影级数减少；同一效果需要 WGSL 与 GLSL 两份着色器（ARCHITECTURE §10.3），**维护成本约 ×2**，且 draw call 开销更高（预算低 20–30%，§13.5）。Low 档（Iris Xe 级核显）又默认走 WebGL2，**最弱硬件配最弱路径**，30 fps 目标最危险。
- **触发信号**：M0 单块地形在 Iris Xe + WebGL2 下 < 30 fps；WebGL2 与 WebGPU 的视觉回归差异被评审判为"不是同一个游戏"；任一效果的 GLSL 版本落后 WGSL 版本超过一个里程碑。
- **缓解方案**：
  1. 设计阶段就把"WebGL2 能做什么"当作**画质下限**：Low 档不依赖任何 compute 特性；Low/Medium 的美术预算（植被密度、阴影级数、粒子数）按 WebGL2 定。
  2. 每个着色器效果的任务验收标准里**必须同时包含两条路径的截图与帧时间**（视觉回归在 CI 中跑两条路径）。
  3. 建一个"双路径一致性"清单（效果名、WGSL 文件、GLSL 文件、最后一次对齐的提交），Fable 审阅时抽查。
  4. 把预计算替代 compute：建筑遮挡体（MAPS §1.6 `occluders`）、烘焙高度雾、预烘焙阴影贴图（静态部分）。
- **应急预案**：若 M0 证明 Iris Xe 无法达到 30 fps（H-021 设备实测）→ **把 Low 档目标降为 720p / 25–30 fps 并明确标注"最低体验"**，或把最低支持 GPU 上调到 GTX 1650 级（需人决定并写入官方系统需求，H-039）；若 GLSL 维护失控 → 冻结 WebGL2 路径的新效果，只做 bug 修复。
- **对应文档**：ARCHITECTURE §10.3、§13.1、§13.5、§20 #3。

### R-03 着色器/管线编译卡顿

类别：技术｜概率：中｜影响：中｜最晚验证：M0｜负责方：执行者

- **描述**：首次出现的材质变体/渲染管线会触发数十–数百 ms 掉帧（ARCHITECTURE §20 #4）；驱动更新后着色器缓存失效，首次启动再次变慢；WebGL2 的同步链接比 WebGPU 的异步创建更容易出现卡顿。
- **触发信号**：M0 固定机位录屏逐帧分析出现 > 50 ms 的单帧；`webgpu.createRenderPipelineAsync` 完成数少于变体数；运行时变体计数 > 60（硬指标，ARCHITECTURE §10.4）。
- **缓解方案**：
  1. 变体上限 ≤ 60，由 CI 统计，超限即失败（§10.4）。
  2. 加载界面期"虚拟网格遍历全部变体"预热，**预热完成才允许进入部署界面**；预热进度条算作加载一部分。
  3. WebGL2 使用 `KHR_parallel_shader_compile`（如可用）轮询；禁止运行时拼接/生成着色器源码。
  4. 在遥测中记录"首次出现的变体编译耗时"分布（可选，见 ARCHITECTURE §18.3）。
  5. M0 任务 `shader-warmup-test`：冷缓存（清理浏览器数据）与热缓存各跑 5 次，记录首 60 秒内 99 分位帧时间。
- **应急预案**：若预热时间 > 15 s 影响体验 → 减少变体（合并宏），或把"低频变体"（雨、雪等）延后到该地图专属加载阶段；仍不行则把过渡性的"编译卡顿"藏在出生倒计时/过场里。
- **对应文档**：ARCHITECTURE §10.4、§20 #4。

### R-04 浏览器内存上限与标签页崩溃

类别：技术｜概率：中｜影响：高｜最晚验证：M0｜负责方：执行者（主）、人（低内存机器）

- **描述**：三类上限叠加：①JS 堆（计划 ≤ 1.5 GB，T5）；②WASM 线性内存（wasm32 理论 4 GB，计划上限 1.5 GB；实际可分配量因浏览器/系统而异，**未核实**）；③GPU 显存（浏览器**无精确查询 API**，只能自估，ARCHITECTURE §10.3）。超限时浏览器直接杀标签页（"Aw, Snap"），玩家无任何提示，对局中丢人。Low 档目标机型只有 8 GB 系统内存（T4）。
- **触发信号**：M0 内存剖析（Chrome `performance.measureUserAgentSpecificMemory`、任务管理器）显示稳态 > 档位预算（Low 0.9 GB、Med 1.2 GB、High/Ultra 1.5 GB，§13.3）；加载 10 分钟后 RSS 持续单调增长（泄漏）；显存估算 > 档位预算 90%。
- **缓解方案**：
  1. 严格执行 ARCHITECTURE §13.3 / §13.4 预算；纹理上传 GPU 后释放 CPU 副本；区块解码缓冲池化（128 MB 环形缓冲）；`.fpak` 分块 LRU 淘汰。
  2. 自估显存预算器：每次纹理/缓冲创建登记字节数，超出档位预算 90% 自动降低 mip 上限/阴影分辨率/植被密度（"动态降级"而非崩溃，§13.2）。
  3. M0 任务 `memory-soak`：连续 60 分钟在 100 bot 视角切换场景下运行，每 30 s 采样内存，生成曲线；超预算或有泄漏趋势则阻断 M0 验收。
  4. 页面可见性：标签页后台时释放非必要缓存、暂停渲染。
  5. 提供"低内存模式"开关（强制 Low 档资源包，不下载 High 纹理）。
- **应急预案**：Low/Medium 档仍崩溃 → 降低同屏角色上限（≤ 60 LOD0–2 → ≤ 40）、缩短流式加载半径、关闭植被 impostor 以外的细节；仍不行则**上调最低内存要求到 16 GB 并在启动页拦截并说明**（需人决定，H-039）。
- **对应文档**：ARCHITECTURE §13.2–13.4、§20 #2、T4、T5。

### R-05 主线程单线程瓶颈与 WASM 线程（COOP/COEP 跨源隔离）

类别：技术｜概率：高｜影响：中｜最晚验证：M0｜负责方：执行者

- **描述**：JS 主线程同时负责 Babylon 渲染提交、UI（Preact DOM 覆盖层）、输入、网络解包、WASM 预测。ARCHITECTURE §20 #3 给出渲染 CPU 预算 ≈ 4.5 ms。**WASM 多线程（`wasm-bindgen-rayon` 等）需要 `SharedArrayBuffer`，而它要求页面"跨源隔离"（响应头 `Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp`，或 `credentialless`）**。启用后的连带影响（均需以 M0 实测为准）：
  - 所有跨源子资源（CDN/R2 上的 `.fpak`、字体、脚本）必须带 `Cross-Origin-Resource-Policy` 或 CORS 头，否则被拦；
  - 以弹窗方式的 OAuth 登录（Discord/Google）会因 COOP 隔离而丢失 `window.opener` 通道，只能改用整页重定向流程；
  - 第三方嵌入（iframe、统计脚本、LiveKit 的 CDN 脚本）会被 COEP 拦截——本项目设计为**零第三方脚本、LiveKit 客户端 SDK 自托管打包**（ARCHITECTURE §19.5），所以影响可控，但一旦将来想嵌入第三方（视频、社交按钮、广告）就会撞墙；
  - 部分浏览器对 `credentialless`/隔离的支持程度**未核实**。
  因此**当前设计决定：不依赖 SharedArrayBuffer（ARCHITECTURE §19.5、§20 #3）**，预测 WASM 只算本地玩家，大计算放 GPU compute 与 Worker（解码、流式）。
- **触发信号**：M0 帧时间分解（performance.mark）显示主线程 JS 时间 > 6 ms（High 档）；UI 更新使帧时间抖动 > 2 ms；WASM 预测单帧 > 1 ms；WebGL2 路径主线程 > 8 ms。
- **缓解方案**：
  1. 把 Worker 用到位：纹理转码（BasisU transcoder）、网格解码（Meshopt）、`.fpak` 解包、音频解码全部在 Worker；用 `postMessage` + `Transferable`（不依赖 SAB）。
  2. `OffscreenCanvas` 渲染到 Worker 的可行性做 M0 spike（Babylon 对 OffscreenCanvas 的支持程度**未核实**），结果写入 ARCHITECTURE §20；若可行，评估把整个渲染放 Worker、主线程只做 UI。
  3. UI 预算严格（UI_SPEC §8）：DOM 节点数、更新频率、禁止强制同步布局；战术地图用单独 Canvas。
  4. 若未来要启用 SAB：先做一个 `?isolated=1` 实验，整页验证 CDN 头、OAuth（改整页重定向）、LiveKit 是否正常，再决定；**在决定前不得让任何功能依赖 SAB**（Fable 审阅检查点）。
- **应急预案**：主线程超预算 → 降低 UI 更新频率（HUD 30 Hz → 15 Hz）、降低同屏角色上限与动画更新频率、把粒子/植被全部交给 GPU；若 OffscreenCanvas 方案验证可行但工作量大，列入 M2 的重构任务；若走 SAB 路线，则在 `docs/ARCHITECTURE.md` 新增"跨源隔离清单"章节并由人确认 OAuth 流程改版（H-063）。
- **对应文档**：ARCHITECTURE §19.5、§20 #3、§13.5。

### R-06 100 人带宽与服务器 CPU

类别：技术｜概率：中｜影响：高｜最晚验证：M2（M0 做早期 gate）｜负责方：执行者

- **描述**：设计目标：每玩家下行均值 ≤ 256 kbps、峰值 ≤ 512 kbps；单局稳态服务器 ≤ 18 ms/tick（预算 33.3 ms，ARCHITECTURE §6.10），推算 ≈ 16.4 ms 且余量 ≈ 51%——**这些是设计估算，未经实测（§20 #14）**。主要不确定项：Rapier KCC 每玩家 ≈ 20 µs 的假设、快照编码并行度、bot 思考 3 ms 假设、QUIC 加密开销、AOI 排序、载具悬挂（≤ 40 辆）。一旦 tick 超限，服务器降频到 15 Hz 出包（§6.6.3），手感立刻恶化。
- **触发信号**：M0 `headless-client` 100 连接 × 20 pkt/s 下 `server_tick_ms` P99 > 28 ms（§18.3 告警线）；`net_bytes_out_per_client` P99 > 400 kbps；`aoi_starved_total` 持续增长；单局 CPU > 1.5 核等效。
- **缓解方案**：
  1. M0 就做"空壳压测 gate"：用最简实体（只有 KCC + 快照）跑 100 个 headless-client，建立 CPU/带宽基线；**该 gate 通过前不得在服务器上堆叠规则**。
  2. M2 100 人完整压测任务（`headless-client` + 60 bot + 40 载具 + 400 弹体）：产出每阶段耗时分解，对照 §6.10 表逐行回修文档。
  3. 预留降级旋钮并**写入配置**：出包频率（20→15→10 Hz）、AOI 半径、远距降频、弹体合并上限、bot 思考分片；旋钮由监控自动触发并告警。
  4. 带宽：协议 `protocol` crate 做位级量化 + 基线增量；M0 即用真实消息统计各类消息占比，防止某类（如载具、爆炸事件）吞掉预算。
  5. 服务器硬件基准写入 T3：≥ 4 个高频物理核；在候选机房租小时机型做真实机器压测，而非用开发机推算（H-016）。
- **应急预案**：①降低单局人数（100→80，50v50→40v40，需人决定）；②每机 2 局降为 1 局；③bot 数量上限下调；④载具上限（≤ 40）下调；⑤"降频保护"自动启用并在玩家界面显示"高负载"提示。M2 若不达标，**不得进入 M3**。
- **对应文档**：ARCHITECTURE §5.6、§6.9、§6.10、§18.1、§20 #14。

### R-07 WebTransport 可用性与 UDP/HTTP3 被阻断

类别：技术｜概率：中｜影响：中｜最晚验证：M0｜负责方：执行者（主）、人（受限网络测试环境）

- **描述**：WebTransport 依赖 QUIC（UDP/443 等）。企业网络、校园网、部分运营商、部分 VPN/代理会阻断或限速 UDP/HTTP3；Safari 26.4 才进入 Baseline（"newly available"≠广泛可用，ARCHITECTURE §5.0），各引擎的证书要求、datagram 大小（`maxDatagramSize`）细节差异**未核实**；`wtransport` crate 的成熟度与互通性是 M0 退出条件（§20.1 #1）。WebSocket 兜底存在队头阻塞（§20 #7），手感下降但可玩。
- **触发信号**：M0 在 Chrome/Firefox/Safari × （家庭宽带 / 手机热点 / 企业代理 / 禁 UDP 防火墙）的矩阵中，WT 连接成功率 < 100% 的组合；WS 兜底下 RTT P95 比 WT 高 > 50 ms 或丢包重传导致输入延迟 > 100 ms；QUIC 握手失败占比（遥测 `传输类型 wt/ws`）> 20%。
- **缓解方案**：
  1. 连接逻辑：并行竞速（WT 尝试 ≤ 2 s，失败则 WS），结果缓存在 localStorage（per-viewer 便利，需 try/catch），并在设置里可强制 WS。
  2. WS 路径是**一等路径**（§5.0 结论 2）：同一消息层、CI 里 100% 回放测试同时跑 WT 与 WS；WS 路径的拥塞策略（"最新者优先"丢弃、冗余输入）专项测试。
  3. 建立"受限网络测试台"（H-022）：一台禁用 UDP 的路由/防火墙规则、一个 HTTP 代理；手机热点测试清单。
  4. 服务器同时监听 TCP/443（WS）与 UDP/443（WT）；TLS 证书使用受信任 CA（Let's Encrypt），**不依赖 `serverCertificateHashes`**（仅本地开发，各浏览器支持未核实，§18.2）。
  5. HUD 显示传输类型与 RTT，便于玩家与支持排障。
- **应急预案**：若 `wtransport` 互通性不达标 → 先用 WS-only 发 M1（带宽预算 §6.9 需复核 WS 开销），WT 作为后续优化；若 WS 兜底体验差 → 对 WS 用户降低出包频率并在 UI 提示"网络受限"。
- **对应文档**：ARCHITECTURE §5.0、§5.5、§6.6、§18.2、T6、T7、§20.1 #1。

### R-08 Rapier 原生/WASM 不一致致预测误差

类别：技术｜概率：中｜影响：中｜最晚验证：M0｜负责方：执行者

- **描述**：客户端用 WASM、服务器用原生，同一份 `sim` 代码。即使开启 `enhanced-determinism`，两种目标的浮点行为（FMA、编译器优化、SIMD 开关）仍可能产生微小差异；复杂地形接触、台阶/斜坡、载具上下、被推挤时误差被放大，表现为玩家被服务器"拽回"（rubber-banding）。BRIEF R5 与 ARCHITECTURE T1 **已规定不要求逐比特一致**，按容差对账（位置误差 > 0.05 m 触发回滚重放）；风险在于容差内的误差累积、以及回滚重放成本（CPU）过高。
- **触发信号**：M0 "10 分钟随机输入回放"位置漂移 RMS > 2 cm/s 平均（§20.1 #3）；真实 RTT 80 ms 下每分钟回滚次数 > 阈值（例如 > 6 次/分钟，**阈值待 M0 定**）；KCC 单次耗时 > 20 µs/玩家（§20.1 #2）。
- **缓解方案**：
  1. M0 任务 `determinism-harness`：同一输入序列分别在原生与 WASM 上跑，输出位置轨迹差异直方图；覆盖平地/斜坡/台阶/贴墙/跳跃/翻越/趴下切换。
  2. 把"会放大误差"的操作（翻越、攀爬、载具上下、爆炸击退）设计成**服务器权威的短过渡**（客户端只做动画预测，位置由服务器给出），减少预测面。
  3. 对账平滑：误差 < 阈值时用视觉平滑（插值修正）而非瞬移；仅在阈值以上才硬回滚。
  4. 构建配置固定：同一 Rust 工具链版本、禁用 fast-math、在 CI 中固定 WASM/原生的编译 flag；`/data` 哈希相同才允许连接。
  5. 只保证"同构建 WASM vs WASM"逐比特一致（回放、CI），不要把"原生与 WASM 一致"写入任何验收标准（T1）。
- **应急预案**：若漂移过大 → 缩小客户端预测范围（只预测水平移动与开火，不预测碰撞细节）、增大对账容差并加强平滑；极端情况下改为"服务器权威 + 客户端仅插值/输入平滑"（手感下降，延迟高时更明显）。
- **对应文档**：ARCHITECTURE §5.3、§6.4、T1、§20 #9、§20.1 #2–#3。

### R-09 载具物理稳定性

类别：技术｜概率：高｜影响：中｜最晚验证：M1（1 辆坦克）、M3（全载具）｜负责方：执行者

- **描述**：载具用"自写 raycast 悬挂 + 履带模型"（总纲 §3），不是现成物理载具控制器。坦克质量大、接触点多，常见问题：抖动/爆炸性抖动、斜坡侧翻、翻转后无法复位、卡地形、乘员出入造成位置突变、网络同步抖动（40 辆 × 4–8 悬挂射线 = 预算 2.0 ms，§6.10）、预测难（客户端驾驶员的预测与服务器偏差）。
- **触发信号**：M1 单辆坦克在 MAPS Carentan 1/3 区域内：连续 10 分钟随机驾驶出现 NaN/穿地/飞天；陡坡（> 25°）下溜车或翻车比例 > 5%；多人同车时位置误差持续上升；服务器载具阶段 > 2 ms。
- **缓解方案**：
  1. M1 任务 `vehicle-sandbox`：独立测试场景（斜坡、台阶、树篱缺口、桥、泥地），自动化脚本驾驶 + 断言（速度、姿态、最大穿深）。
  2. 简化物理优先：悬挂/履带用"稳定第一"的参数（速度钳制、角速度钳制、质心下移、自动防翻），**宁可略显"漂"也不要抖**；先做稳定再做真实。
  3. 驾驶员预测只预测"控制输入→本地模拟"，其它乘员/观察者只看服务器快照插值；载具位置误差大时用更激进的平滑。
  4. 复位机制：翻车 5 s 后可请求自动复位（GAMEDESIGN 载具章节未必有，作为设计建议提交 Fable 审阅）。
- **应急预案**：M1 若 3 周内仍不稳定 → 降级为"贴地 kinematic 载具"（沿地形高度图 + 坡度限速、不模拟侧翻），保留炮塔/装甲系统；M3 再恢复物理细节。
- **对应文档**：总纲 §3、GAMEDESIGN §14、ARCHITECTURE §5.3、§6.10。

### R-10 TAAU 自研难度

类别：技术｜概率：高｜影响：低｜最晚验证：M2｜负责方：执行者

- **描述**：自研时间性超分（TAAU，WebGPU compute）需要运动向量、抖动序列、历史重投影、邻域颜色钳制、去鬼影、植被/透明物体特殊处理；在 Babylon 上无现成实现，且植被密集的树篱/森林是 TAA 最容易闪烁/拖影的场景。调参量大，容易吃掉一个月。
- **触发信号**：M0/M1 spike 中，Carentan 树篱场景静止镜头闪烁、转动时鬼影明显；TAAU 在 RTX 3060 上耗时 > 1.5 ms（1080p 内部 67%）；与 FSR1 式空间放大的主观对比无明显优势。
- **缓解方案**：
  1. 里程碑分级：M0 只做"TAA 或纯空间放大"；M2 评估自研 TAAU；**自研 TAAU 不进入任何里程碑的验收必要项**（只做"优先级可砍"项）。
  2. 先做 FSR1 式空间放大 + 锐化 + 轻 TAA，作为所有路径的默认；TAAU 作为 High/Ultra 的可选。
  3. 植被使用 alpha-to-coverage/抖动淡入以减少 TAA 闪烁；运动向量对植被摆动单独处理。
  4. 评估 Babylon 内置 TAA 后处理是否够用。
- **应急预案**：TAAU 质量不达标 → 直接砍掉，用"原生分辨率 + FXAA/SMAA + 动态分辨率（空间放大）"；画质档位表中去掉 TAAU 一行（需回写 ARCHITECTURE §13.1）。
- **对应文档**：ARCHITECTURE §5.11、§10.1–10.2、§13.1。

### R-11 音频延迟与 Safari 解码差异

类别：技术｜概率：中｜影响：低｜最晚验证：M1｜负责方：执行者

- **描述**：WebAudio 输出延迟 10–40 ms 起，蓝牙可超 150 ms（ARCHITECTURE §12.6）；Safari 对 Opus（WebM 容器）的 `decodeAudioData` 支持程度随版本而异（`ASSET_SHOPPING_LIST §7.2` #15 要求实测）；D-AUD 规定 Opus 为主、AAC 兜底，启动时用 `decodeAudioData` 实测探测。AudioWorklet 遮挡低通/压制在低端机上可能抢占主线程时间片；自动播放策略（需用户手势才能 `resume()`）。
- **触发信号**：M1 在 Safari/Firefox/Chrome 上探测失败比例 > 0；`audioContext.outputLatency` 大于 100 ms 的设备占比（遥测）；远距枪声（声速延迟）与本地枪声相位错位导致"双枪声"；AudioBuffer 内存超预算（§12.7 首图 ≈ 18 MB Medium）。
- **缓解方案**：
  1. 启动探测（D-AUD）：用一段极短 Opus-in-WebM 与 AAC 样本跑 `decodeAudioData`；结果缓存；音频包在 `.fpak` 中按格式准备两套**不现实**（体积翻倍）——因此**只下发探测通过的那一种**：服务器清单按格式分流，让 `asset-pipeline` 同时产出 Opus 包与 AAC 包，CDN 按需下发。
  2. 本地开火音在 `fire.local` 立即触发（§12.6），远程枪声叠加声速延迟；对本地玩家附近 < 30 m 的其他人枪声不加额外延迟，避免"双响"。
  3. 复音上限与偷声（§12.4），卷积混响仅 3 套 IR。
  4. 蓝牙耳机用户：设置里提示"检测到高延迟输出，建议有线"。
- **应急预案**：Safari 解码路线不通 → Safari 用户走 AAC 包；仍不通 → Safari 标注"音频不完整支持"，不阻塞发布（Safari 是"尽力支持"，A4）。
- **对应文档**：ARCHITECTURE §12、总纲 D-AUD、ASSET_SHOPPING_LIST §3.3 C4、§7.2 #15。

### R-12 Pointer Lock / 键盘限制

类别：技术｜概率：中｜影响：中｜最晚验证：M0｜负责方：执行者

- **描述**：UI_SPEC 附录 B 明确列为"未核实"：各浏览器对 Pointer Lock 的重锁冷却、`unadjustedMovement`（原始鼠标输入）、Keyboard Lock API、`navigator.keyboard.getLayoutMap()`、鼠标侧键后退拦截的支持与行为。已知通用限制（需实测确认）：Esc 会退出 Pointer Lock 且无法拦截；退出后立即重锁可能被浏览器拒绝（冷却）；`Ctrl+W`、`Alt+F4`、`Ctrl+Tab`、`F11`/系统快捷键常无法被页面接管（Keyboard Lock 通常需要全屏，支持度未核实）；窗口失焦、全屏切换、多显示器；非美式键盘布局（WASD 位置）。这些直接影响 FPS 的"能玩"程度。
- **触发信号**：M0 输入测试在 Chrome/Edge/Firefox/Safari × Windows/macOS/Linux × 多种键盘布局（QWERTY/AZERTY/QWERTZ）上，出现：无法稳定重锁、鼠标加速度不可关、侧键触发"后退"离开页面、全屏下快捷键冲突。
- **缓解方案**：
  1. M0 任务 `input-matrix`：自动化 + 手工清单覆盖上述矩阵，输出支持表写入 UI_SPEC 附录 B 对应条目。
  2. 绑定键位走 `KeyboardEvent.code`（物理键位）而不是 `key`；提供"改键"；用 `getLayoutMap()` 显示正确字符（不可用则回退）。
  3. 重锁策略：Esc 打开暂停菜单（UI_SPEC §5.5 的行为），点击继续时在**用户手势内**重锁；重锁失败显示"点击屏幕继续"。
  4. 阻止浏览器默认行为：`preventDefault` 于游戏用键；`beforeunload` 提示离开确认；侧键 `mouse back/forward` 拦截（如不可行，在文档中声明并在设置里提示）。
  5. 高 DPI 与鼠标原始输入：`requestPointerLock({unadjustedMovement:true})` 可用则用，不可用则回退并在设置里提供加速度补偿提示。
- **应急预案**：某浏览器无法稳定 Pointer Lock → 在启动页对该浏览器提示"推荐使用 Chrome/Edge"，不阻塞发布；Keyboard Lock 不可用 → 提供"建议使用全屏 + 记住 Esc 行为"的引导页面。
- **对应文档**：UI_SPEC §5.5、附录 B #2–#3、ARCHITECTURE A4。

### R-13 首包与流式加载体积

类别：技术｜概率：高｜影响：中｜最晚验证：M1｜负责方：执行者

- **描述**：目标：主菜单 ≤ 8 MB（gzip/br）、首图 Medium ≤ 150 MB、High ≤ 350 MB、Ultra ≤ 600 MB（ARCHITECTURE §11.4）。**首图 150 MB 对"点开链接就能玩"的浏览器游戏仍然偏大**：家庭宽带 50 Mbps 下约 24 s+，移动热点/弱网体验差；High/Ultra 更大。素材采购（带内饰坦克、高精度枪械）会推高体积；`.fpak` 分块与 HTTP Range 流式带来额外实现复杂度；浏览器缓存可能被清理（Cache API/OPFS 配额）。
- **触发信号**：M1 manifest 体积门禁（> 1% 增量即失败，§11.4）反复触发；首图 Medium 实测 > 150 MB；冷启动到"可部署"时间 > 60 s（50 Mbps）；CDN 命中率低；OPFS/Cache 配额被驱逐。
- **缓解方案**：
  1. CI 体积门禁（§11.4 已规定）；每个素材采购项在 LICENSES 表之外**加一列"处理后体积"**（执行者在 ingest 时填写）。
  2. 渐进式加载：先下 Low 级 mip 与 LOD，进入部署界面后后台补高 mip；出生点附近区块优先（§9.4 "出生即用"）。
  3. 首图分层：部署界面所需最小集（地形低模、HQ 附近、出生点附近）先行；其余按距离环流式加载。
  4. 持久化缓存：`navigator.storage.persist()` 请求；缓存校验用内容哈希，增量更新（`.fpak` 分块哈希）。
  5. 预算按里程碑回收：每个里程碑末列出体积 Top 20 资产，Fable 审阅是否值得。
- **应急预案**：Medium 超限 → 降低植被/道具密度与贴图分辨率，砍掉次要载具与武器皮肤；对 100 MB+ 首次下载加"首次下载中，预计 N 分钟"进度与可取消说明；仍不行则**把 Medium 首图收窄为小区域（先加载 1/3 地图，见 MAPS §3.8）**。
- **对应文档**：ARCHITECTURE §11.4–11.6、§9.4、总纲 §3 资源管线。

### R-14 移动设备不支持（预期管理）

类别：技术｜概率：高｜影响：低｜最晚验证：上线前｜负责方：人（决定文案）、执行者

- **描述**：A4 明确不支持手机/平板（无触控输入层、无手柄）。但**玩家会用手机/平板点开链接**，如果页面白屏或崩溃，会产生差评与"游戏坏了"的印象；iPadOS + 键鼠的用户也可能尝试。
- **触发信号**：遥测/访问日志显示 UA 为移动设备的比例 > 5%；反馈渠道出现"打不开"。
- **缓解方案**：启动页能力探测（指针类型、`maxTouchPoints`、屏幕尺寸、WebGPU/WebGL2、内存估计）→ 明确的"需要桌面浏览器 + 键鼠"提示页，提供"复制链接稍后在电脑打开"按钮与一个可在手机上观看的静态介绍（截图/说明）；不在手机上下载任何游戏资源（节省流量）。
- **应急预案**：若某一类设备（如带键鼠的 iPad）需求强烈 → 作为 Backlog 评估，不影响 M4。
- **对应文档**：总纲 A4、ARCHITECTURE A4、UI_SPEC §4.1（启动页）。

### R-15 Babylon.js 引擎层依赖（compute/FrameGraph 成熟度、升级破坏）

类别：技术｜概率：中｜影响：中｜最晚验证：M0｜负责方：执行者

- **描述**：整套渲染建立在 Babylon.js 8.x 的 `WebGPUEngine`、`ComputeShader`、`RenderTargetTexture` 之上；ARCHITECTURE T11 明确其 FrameGraph 成熟度**未核实**，不作为依赖，需自行组织 pass。风险：①compute 与自定义帧图的 API 在小版本间变化；②大型场景的 draw call 提交开销、实例化 indirect draw 能力受引擎抽象限制；③为性能被迫绕过引擎（等于维护半个引擎）；④升级版本引入回归。备选（Three.js WebGPURenderer/TSL、PlayCanvas 等）已在 ARCHITECTURE §5.1 对比，换引擎代价极高。
- **触发信号**：M0 spike（Hi-Z、froxel、TAAU、indirect draw）有 ≥ 2 项在 Babylon 的 API 下无法实现或需要引擎魔改；升级一个小版本需要改 > 10 个文件；引擎 issue 追踪里相关 bug 长期未修。
- **缓解方案**：
  1. M0 spike 清单（执行者逐项写结论到 ARCHITECTURE §20.1 #4）：compute 写纹理、indirect draw、自定义 render pass 顺序、`RenderTargetTexture` 多 MRT、GPU 蒙皮角色大量实例化。
  2. **锁定 Babylon 小版本**（ARCHITECTURE §19.5）；升级只在里程碑之间进行，并有"升级任务"含视觉回归。
  3. 渲染层封装：`/client/src/render` 对上层暴露窄接口（不让游戏逻辑直接依赖 Babylon 对象），降低替换/补丁成本。
  4. 保持对关键引擎部分打补丁的能力（`patch-package` 或 fork 记录），所有补丁在文档中登记。
- **应急预案**：M0 判定某关键特性不可行 → 回退到没有该特性的设计（例如不用 Hi-Z、改用预计算遮挡体），并更新 §13.5 预算；如果整体不行，**M0 结束时是"换引擎"的唯一低成本窗口**（Fable 审阅 + 人决定，H-038）。
- **对应文档**：ARCHITECTURE §5.1、T11、§10.1、§20.1 #4。

### R-16 语音（LiveKit）集成、订阅延迟与浏览器差异

类别：技术｜概率：中｜影响：中｜最晚验证：M2｜负责方：执行者

- **描述**：对局服务器通过 LiveKit Server API 按"小队/指挥/车组频道 + 近距离 ≤ 50 m"**动态**设置订阅权限（ARCHITECTURE §14.2）；订阅更新延迟视为 < 300 ms（T8，估计值**未核实**）；100 人 × 近距离空间化的订阅集合更新频率高，API 调用量可能触发限流；Safari 的 WebRTC 扩展（Insertable Streams、SVC）落后（二手来源，未核实），本设计只用基础 Opus；用户麦克风权限、回声消除、蓝牙；COOP/COEP 对 LiveKit 的影响见 R-05。
- **触发信号**：M2 压测中订阅更新 P95 > 500 ms；`livekit_api_errors_total` 错误率 > 1%（§18.3）；近距离语音在人群密集区"忽有忽无"；多人同时说话时混音 CPU 过高（同时最多混 8 路）。
- **缓解方案**：
  1. 订阅集合计算只在"集合变化超过阈值"（距离穿越 40/60 m 的滞回）时才调用 API；批量更新；服务器侧去抖。
  2. 降级顺序（ARCHITECTURE §14.5 已有思路）：近距离语音 → 仅小队/指挥频道 → 仅文字。
  3. M2 前做 LiveKit 自托管容量测试（`T8` 的实测）与"同机房 RTT < 5 ms"验证。
  4. 麦克风接入：按需请求权限、提供推键说话（PTT）与语音激活（VAD）、自测回放；Safari 单独测试矩阵。
- **应急预案**：近距离语音不稳定 → 首发关闭近距离语音，只留小队/指挥/车组（对 Frontline 玩法影响较小）；LiveKit 容量不足 → 提高机型或限制并发语音用户数；若 LiveKit 自托管运维负担过大 → 评估 LiveKit Cloud（需账号，H-018；费用未核实）。
- **对应文档**：ARCHITECTURE §14、T8、T9、§18.1。

### R-17 依赖许可证与成熟度（wtransport 等）、供应链

类别：技术｜概率：中｜影响：中｜最晚验证：M0｜负责方：执行者（主）、人（对个案许可证裁决）

- **描述**：LICENSES.md §5 的依赖许可证**全部是凭记忆、未核实**；`wtransport` 的许可证明确标"必须实测，不得凭记忆放行"。拟议政策：默认禁止 GPL/AGPL 进入客户端 WASM 与前端打包；LGPL/MPL 个案评估。成熟度风险：`wtransport`、`bevy_ecs` 独立使用、`rapier` 的 WASM 构建体积；供应链攻击（npm/crates 恶意包）、传递依赖爆炸。

  2. 锁文件进库；`cargo-deny`（许可证 + 漏洞）、`npm audit`/`osv-scanner` 进 CI；第三方脚本零（全部自托管）。
  3. 对 `wtransport` 建立替代路线备忘（直接用 `quinn` + `h3-webtransport`，或先 WS-only）。
  4. 对"需个案评估"类许可证，由人在 LICENSES §5 的政策下逐案裁决（H-037）。
- **应急预案**：核心依赖许可证不兼容 → 替换依赖或购买商业许可；若 `wtransport` 无法使用 → R-07 的"WS-only 发 M1"预案。
- **对应文档**：LICENSES §5、ARCHITECTURE §5.5、§19.5。

### R-18 全部性能/带宽预算为设计估算，未经实测

### R-20 1944 地貌修正与树篱/洪泛人工量

- **对应文档**：MAPS §1.5、§3.7、§3.8、§7、§9.1。

### R-22 付费许可与网页分发的冲突（`.fpak` 非 DRM）

类别：素材｜概率：中｜影响：高｜最晚验证：M0｜负责方：人（主）、执行者（技术措施）

- **描述（这是素材线上最核心的合规风险）**：TurboSquid、CGTrader（Royalty Free）、MoCap Online、Unity Asset Store 的条款要求素材"必须嵌入产品、第三方不能单独提取"；音频渠道（A Sound Effect、Sonniss、BOOM、Artlist、Soundsnap）禁止"以独立可提取形式再分发/放入库/音效板"。**浏览器游戏的资源必然落在玩家的缓存与 DevTools 里，技术上不可能做到"无法提取"**（ASSET_SHOPPING_LIST §3.4）。D-PAK 的 `.fpak` 自有分块容器、哈希命名、剥离元数据、不提供下载入口，仅是**合规层面的"非独立文件分发"**，**不是 DRM**，无法阻止有决心的提取者；本次检查的所有渠道文本中，**没有任何一家直接讨论过"网页游戏资源落在玩家浏览器缓存里"这一场景**。TurboSquid 明文仅豁免 Unity/Unreal/Lumberyard/Stingray 的 WebGL 导出，"Other open formats are prohibited"，glTF/KTX2 直发属灰区甚至违反。
- **触发信号**：卖家回复"不允许"或"需要定制/扩展许可"；卖家邮件要求把素材"加密/DRM"；有第三方在网上发布从我们游戏中提取的素材（上线后）；某卖家投诉/DMCA。
- **缓解方案**：
  1. **采购策略（D-LIC）**：优先 CC0（Poly Haven、ambientCG）与 Fab Standard；对"慎用"渠道**先发邮件拿到书面确认再付款**（ASSET_SHOPPING_LIST §6 模板），确认邮件要点含"玩家可在 DevTools/缓存中看到包文件"这一事实的明示，让卖家在知情下确认。
  2. **技术措施**（执行者任务 `asset-pipeline-fpak`）：Meshopt 网格 + KTX2 + 音频一律打包进 `.fpak`；哈希命名、不暴露原始文件名；音频只下发 Opus/AAC 编码后的数据，**剔除 BWAV/iXML/Soundminer 元数据**；源 WAV/源模型永不上传公开 CDN；不提供素材浏览/下载/试听入口；不做音效板；不开放 mod API。
  3. **证据存档**：`LICENSES.md` §1 规定的 `licenses/texts/`、`licenses/confirmations/`、`licenses/receipts/`；在发布流程里记录"证明无意分发"的措施清单（ASSET_SHOPPING_LIST §3.4 第 7 点）。
  4. **范围控制**：把高风险渠道（TurboSquid、ActorCore、KitBash3D、Soundsnap、Pro Sound Effects、Epidemic、Artlist、Zapsplat、Fab 音频）降到"必要才用"；M0/M1 的素材尽量来自绿/黄绿渠道（ASSET_SHOPPING_LIST §3.5）。
  5. **人负责人需要在知情下接受残余风险**（ASSET_SHOPPING_LIST §7.3 #1，H-005）。**这是个需要人明确签字的风险决定，执行者不得自行默认通过。**
- **应急预案**：某卖家投诉/拒绝 → 立即把该素材 `REJECTED`（LICENSES §1），下架包（`OK→REJECTED` 须同时下架已发布的包）并替换；整批素材来源不可用 → 回到 CC0/Fab Standard 的最小集合 + 灰盒占位（ASSET_GAPS §3）；若最终必须"零残余风险"，**唯一彻底方案是只用 CC0/允许再分发的素材 + 外包原创**（成本见 R-21）。
- **对应文档**：ASSET_SHOPPING_LIST §3.2–3.4、§7.3 #1、LICENSES §1、总纲 D-PAK/D-LIC。

### R-23 卖家不回复/拒绝书面确认

类别：素材｜概率：高｜影响：中｜最晚验证：M0｜负责方：人

- **描述**：D-LIC 要求"慎用渠道"的付费素材先拿书面确认，否则 LICENSES 状态保持 PENDING，不进主分支。大量个人卖家（CGTrader/RenderHub/itch.io）可能不回复、回复含糊（"you can use it in games"）、或要求额外费用；多厂牌平台（A Sound Effect）"禁止改编/修改"措辞极严，格式转换/响度标准化/分层混音是否构成 modifying 需要明确。
- **触发信号**：邮件发出 14 天无回复；回复未覆盖 §6 模板的核心问题（浏览器分发/转换处理/多席位）；平台代客户回复为模板话术。
- **缓解方案**：
  1. 现在就发（H-009）：M0 候选卖家全部同时发邮件；每个需求项备选 ≥ 2 个来源；使用 ASSET_SHOPPING_LIST §6 的英文模板，要点含：项目性质、`.fpak` 可见性、加工清单、不做的事、授权数量（1 人 + 自动化执行者）。
  2. 回复含糊的，二次追问"是否同意以下具体表述"，只接受**对具体表述的肯定回答**并存档完整邮件头。
  3. 无回复则状态保持 PENDING，素材不进主分支，改用替代来源或灰盒占位（ASSET_GAPS §3）。
- **应急预案**：关键素材（如第一人称枪械）卖家都拒绝 → 转向外包原创（成本高，见 R-21）或 CC0 通用枪械；整体上调 GAP 决策优先级。
- **对应文档**：总纲 D-LIC、ASSET_SHOPPING_LIST §1.2、§6、§7.2、LICENSES §1。

### R-24 GAP 项无法以现成素材覆盖

类别：素材｜概率：高｜影响：高｜最晚验证：M1｜负责方：人（决定）、执行者（占位）

- **描述**：ASSET_GAPS 共 19 视觉 + 15 音频缺口，其中最致命的：**GAP-V01 带内饰可动坦克**（Sherman/Panzer 等的车长舱、炮塔内部；外包 $3,000–12,000【估算】）、**GAP-V02 诺曼底/阿登建筑模块**（可进入的石屋，外包 $3,000–10,000【估算】）、**GAP-V03 树篱 bocage**（地图标志性，$800–2,500【估算】）、**GAP-V04 冬季美/德角色**（$1,600–5,000【估算】）、**GAP-V06 第一人称高精度武器**（现成"game ready"枪械多为 2k–12k 顶点，只是第三人称品质，不是 30k–80k 三角形带内部结构的第一人称品质，ASSET_SHOPPING_LIST §2.1 #6）、音频缺口（MG34、BAR 全自动、Panzerfaust/Bazooka、击中人体、坦克被击中/跳弹、战场喊话、美式口音 WW2 语音等）。这些决定了游戏**"第一眼"的品质与史实感**，而 A2 禁止自制与 AI 生成。
- **触发信号**：M1 的 Carentan 切片截图在评审时被判"灰盒感明显"；第一人称武器特写近距离模糊/多边形可见；负责人迟迟不对 GAP 做决定（见 R-54）。
- **缓解方案**：
  1. **ASSET_GAPS §3 的灰盒占位约定**：所有 GAP 都有程序化占位，保证玩法与技术验收不被素材阻塞；占位有自动检测（§3.4）以免带到上线。
  2. 按"最早影响"分三批让人做三选一决定（NEEDS_HUMAN H-047、H-058、H-069 的三张决定表）：继续找 / 外包 / 最接近替代品。**建议**默认：V01 替代（外壳 + 简化内饰盒）、V02 M1 灰盒 + 评估外包 1 套、V03 替代（植物包 + Megascans 土堤材质）、V06 M1 先第三人称品质。
  3. 做"替代品的视觉验收"：在 M1 末做一次整体 look-dev 评审（调色、后处理统一，见 R-27），验证替代方案是否可接受。
  4. 对外包：合同必须写明原创建模/录制、无第三方游戏资产、授权范围含网页分发、交付源文件（ASSET_GAPS §1.1）。
- **应急预案**：关键 GAP 不可解（预算/时间） → 缩小范围：Carentan 内饰不进（载具不可进入内部视角，只有外视角 + 炮手瞄具）；建筑只做外壳 + 少数可进入模块；将"第一人称武器"以第三人称品质上线并在后续里程碑逐把补（ASSET_GAPS 默认建议）；音频缺口用 EQ/变调替代（需人接受史实偏差，H-046）。
- **对应文档**：ASSET_GAPS §1.4、§2、§3；ASSET_SHOPPING_LIST §2.1、§7.3。

### R-25 Megascans/Fab 条款或价格变化

类别：素材｜概率：低｜影响：中｜最晚验证：M2｜负责方：人

- **描述**：Megascans 自 2026-11-05 公告恢复永久免费（ASSET_SHOPPING_LIST §3.2；**本次未逐个商品页确认价格为 0**）；Fab Standard License 的"可提取性"条款全文未取得；档位按过去 12 个月总商业收入是否超 US$100,000，**捐赠是否计入"收入"未核实，保守按计入**；旧 Quixel/Bridge 下载的资产受旧许可约束，须从 Fab 重新领取并留存凭证；Fab 音频类 listing 与视觉片段冲突，取保守。
- **触发信号**：Fab 公告变更许可；已领取商品下架或价格变动；EULA 文本版本号变化；年度收入（含捐赠）接近 US$100,000。
- **缓解方案**：领取当天**截图留证**（商品页价格 0、许可证栏 "Standard License"）并存 `licenses/texts/`；每个里程碑末重新抓取一次 Fab EULA 与已用商品页，对比变化（H-050 持续项）；账户收入阈值写入季度检查表。
- **应急预案**：条款恶化 → 已发布版本的素材按旧条款处理（需律师确认是否追溯，**未核实**）；新内容改用 CC0/Poly Haven 替代；极端情况下下架受影响素材并替换。
- **对应文档**：ASSET_SHOPPING_LIST §3.2、§7.2 #1–#3。

### R-26 游戏提取素材混入

类别：素材｜概率：中｜影响：高｜最晚验证：M0｜负责方：人（购买前核对）、执行者（管线检测）

- **描述**：大量 Sketchfab/CGTrader/TurboSquid 上的二战模型是"从某游戏提取"的，**即使标了 CC 也非作者原创、作者无权授权**。ASSET_SHOPPING_LIST 调研者**无法从搜索摘要证明任何一件候选的来源**，也没有打开过任何素材文件。如果混入，后果是被权利人起诉/下架，且违反总纲 §1 对参考作品的红线（"禁止素材提取"也会被混淆）。
- **触发信号**：素材命名/贴图后缀符合游戏式命名（`_cm`、`_gls`、`_nml`）；网格拆分异常、含隐藏骨骼；卖家资料页无作品集；卖家拒绝书面声明"原创建模"；Reverse image search 命中游戏截图。
- **缓解方案**：
  1. 购买前必走 ASSET_SHOPPING_LIST §2.3 的"疑似游戏提取识别检查表"（7 条），在 LICENSES `notes` 写"已按 §2.3 核对"；卖家书面声明"原创建模，无第三方游戏资产"（§6.1 模板包含）。
  2. 管线 `asset-pipeline ingest` 加自动启发式：贴图/网格命名模式、隐藏骨骼数、材质名中的游戏关键词；命中则标记 PENDING 阻断（执行者任务）。
  3. 对参考作品的素材类词（Call of Duty、Hell Let Loose、Battlefield 等）做卖家页面关键字过滤。
  4. 严禁任何人（含人负责人、执行者）为"参考"而打开/提取参考作品的素材（REFERENCE_MEASUREMENTS §1.2）。
- **应急预案**：发现疑似提取素材 → 立即 `REJECTED` 并下架含它的 `.fpak` 包、重新构建；保留台账行防止重复购买；通知卖家平台；如已公开发布，需评估对外说明并咨询律师（H-040）。
- **对应文档**：ASSET_SHOPPING_LIST §2.3、§6.1、LICENSES §1、REFERENCE_MEASUREMENTS §1.2。

### R-27 素材风格不统一

类别：素材｜概率：高｜影响：中｜最晚验证：M1｜负责方：人（审美定稿）、执行者

- **描述**：A2 要求"只用现成素材"，素材来自 Fab/CGTrader/RenderHub/Poly Haven/Megascans 等十余个来源：不同的比例尺、贴图 texel 密度、PBR 参数口径、材质污渍程度、人物写实度与脏旧程度，放在同一场景会"拼贴感"。ARCHITECTURE §20 #10 的缓解：用材质/调色/后处理统一风格；缺失物件用占位 + 程序化变化。
- **触发信号**：M1 切片里相邻物体的 texel 密度差 > 2 倍；金属度/粗糙度分布明显不同；人物与武器的色调不协调；评审用"盲看截图能否辨出多来源"。
- **缓解方案**：
  1. **美术风格圣经**（H-043、H-044，由人拍板）：基调色板、对比度、脏旧程度、LUT/调色方向；执行者据此做全局调色 LUT 与材质参数归一化。
  2. 管线中做 PBR 归一化：统一 texel density 目标（例如 512 px/m 目标，**数值待定**）、albedo 亮度范围钳制、粗糙度重映射（只用 D-MOD 允许的 `MATPARAM`）。
  3. 采购时优先"成套来源"（同一作者/同一套件），关键资产（武器、角色）尽量同一厂牌。
  4. 里程碑末"视觉一致性评审"：用固定机位截图 + 色板分析（直方图、饱和度分布）量化。
- **应急预案**：风格严重不统一 → 加强后处理（强风格化 LUT、颗粒、色阶）以掩盖来源差异；个别违和素材替换；极端情况下统一到"略风格化"路线（需人决定，H-044）。
- **对应文档**：ARCHITECTURE §20 #10、ASSET_SHOPPING_LIST §2.1。

### R-28 CC-BY 署名遗漏

类别：素材｜概率：中｜影响：低｜最晚验证：上线前｜负责方：执行者

- **描述**：CC-BY 素材（Freesound CC-BY、RenderHub "RC Art - Muzzle Effects" CC-BY 4.0、Fatal Exit "After The War" CC-BY 4.0、OpenAIR 中的 CC-BY 条目等）必须在游戏内 Credits 署名；遗漏即违反许可，且最易被发现。
- **触发信号**：构建时 `credits.json` 缺条目；台账 `chk_attribution=REQUIRED` 的条目 `credit_text` 为空；有素材未登记就进入 `.fpak`。
- **缓解方案**：LICENSES §4.3 的自动汇总与 §4.3(5) 的构建时硬校验（任一失败即构建失败）；CI 中把 `credits.json` 与 `.fpak` manifest 交叉校验；Credits 页中 `required=true` 条目不可被设置项隐藏；里程碑验收前跑一次台账校验（LICENSES §4.4）。
- **应急预案**：发现遗漏 → 立即补署名并发新版本；通知素材作者（若有投诉）；评估是否需要下架。
- **对应文档**：LICENSES §4、ASSET_SHOPPING_LIST §3.2。

### R-29 采购清单本身未核实（价格/质量/型号）

类别：素材｜概率：高｜影响：中｜最晚验证：M0｜负责方：人

- **描述**：ASSET_SHOPPING_LIST §7.1 自述：大量商品页（CGTrader、RenderHub、TurboSquid、Unity、itch.io）无法被 WebFetch 打开，价格/面数/许可均来自搜索摘要；**没有打开任何素材文件**，无法验证模型质量、历史准确性（如 BAR M1918 vs A2、M1903 vs A4 型号吻合度）、UV/贴图/绑定质量、是否游戏提取；音频同理没有试听。部分 URL 是测试环境域名或 404。
- **触发信号**：实际下单页价格与清单差 > 20%；下载后模型打不开、无 UV、无绑定、面数/拓扑与描述不符；音频包文件清单与描述不符（如 "Bullet Bys & Impacts" 并非实枪录制）。
- **缓解方案**：采购流程步骤 1–2（ASSET_SHOPPING_LIST §1.2）在付款前**只买"最便宜的一件做验证"**（先买单件测试管线与质量，再批量）；对音频先看文件清单/试听；购买后第一时间由执行者跑"素材验收脚本"（面数、材质数、UV 检查、骨骼数、尺寸/单位）并回报；不合格在退款窗口内申请退款（各渠道退款政策**未核实**）。
- **应急预案**：质量不合格 → `REJECTED` + 选下一候选；累计 > 2 次同一卖家不合格则放弃该卖家。
- **对应文档**：ASSET_SHOPPING_LIST §1.2、§7.1、§7.2。

### R-30 "不自制"边界（D-MOD）未确认或被越界

类别：素材｜概率：中｜影响：中｜最晚验证：M0｜负责方：人（确认）、执行者（遵守）

- **描述**：D-MOD 默认：允许格式转换、LOD/减面、贴图压缩、重定向、权重传递、材质参数调整、组合装配；不允许从零建模、雕刻、重画贴图、AI 生成。至少有四处灰区待人最终确认：①减面/重绑定/拼装/重材质是否算"自制"（决定 GAP-V01/V02/V04/V05/V06 能否用"买现成 + 加工"解决）；②UI 图标由执行者以 SVG 绘制是否接受；③真人配音/外包录制属"重新录音"，须人决定；④**符号遮盖**：若购入模型/贴图含纳粹符号（见 R-33），去除/遮盖属于"重画贴图"，与 D-MOD 冲突，需要人批准一条明确的例外。另外 **卖家书面确认的"允许加工范围"可能比 D-MOD 更窄**（LICENSES §1 第 8 条要求 `allowed_processing` 不得超过卖家确认范围）。
- **触发信号**：执行者任务回报里出现"为了让它能用，我重画了……/生成了……"；LICENSES `allowed_processing` 与卖家确认范围不一致；人对 D-MOD 迟迟不确认（任务队列里出现大量依赖 D-MOD 的阻塞）。
- **缓解方案**：H-002 在"现在就要做"阶段确认 D-MOD（含符号遮盖例外、UI 图标 SVG 例外）；LICENSES `allowed_processing` 做成**构建硬校验**（处理动作不在列表里则管线拒绝）；执行者任务模板里加"本任务触及哪些 D-MOD 允许动作"字段。
- **应急预案**：越界已发生 → 记录事故，回滚该素材处理产物，状态改 PENDING 并重新评估；若人决定放宽 D-MOD → 先更新 `ASSET_SHOPPING_LIST §2.2` 与 LICENSES，再继续。

### R-31 对标参考作品的整体相似度边界

类别：法律/IP｜概率：中｜影响：高｜最晚验证：M1（咨询）、上线前（并排审查）｜负责方：人（主）、执行者（设计手段）、Fable 审阅（抽查）

- **描述**：一般认为**游戏规则与玩法机制本身不受版权保护**（思想/表达二分；规则、功能性元素通常被认为属于思想/方法，**以律师确认为准**），所以"对标品类玩法"本身是业界常态。风险不在单条规则，而在**整体**：本项目有意识地对标一个具体的参考作品（HLL，见 GAMEDESIGN §0.1）并且要做**"完整对齐 loadout 清单、UI 信息架构与流程"**。如果这些对齐过于细致，累积起来的整体相似度可能引发：①**版权层面的"选择与编排"（selection and arrangement）**——对元素的原创性选取与排列可能获得保护（如整套兵种构成、每兵种的装备槽位与清单的编排、UI 面板信息布局）；②**商业外观（trade dress）/不正当竞争**——整体视觉与体验造成混淆或"搭便车"；③**参考作品 EULA**（见 R-32）；④对内部证据：repo 里明确写"对标 X"、"手感对齐 X"、"UI 流程对齐 X"，在纠纷中会被当作**"有意复制"的证据**，削弱"独立创作"抗辩。注：总纲 §1 已规定：表达层原创（名称、图标、配色、字体、版式、文案、地图关卡布局、能力命名）、黑盒观测、不拆包不抓包。
- **触发信号**：评审者（Fable/人）把本项目截图与参考作品并排放置，"一眼认作同类系统"的元素 > 3 处；兵种/loadout 清单与参考作品逐项重合比例 > 70%（可做对照表自检，**但对照表只放在私有文档**）；UI 面板的信息分区与顺序与参考作品高度一致；外部（玩家/媒体）称其为"HLL 网页版/克隆"；收到律师函或平台投诉。
- **缓解方案（具体设计手段，降低相似度而不损失玩法）**：
  1. **Loadout 独立推导**：每个兵种的装备清单**以真实历史编制（US Army/Wehrmacht TO&E）与武器史实为依据独立编制**，在 `/data/loadouts` 的 `source` 字段记录史实来源；**不得以参考作品的清单为模板逐项对齐**。REFERENCE_MEASUREMENTS 只用来校准"手感量"（射速、致死发数、时序），**不用来复刻"装备清单与槽位结构"**。
  2. **结构性差异**：在不破坏平衡的前提下，主动制造至少 3–4 处**结构性不同**（槽位数量/类型、解锁机制、兵种拆分或合并、小队规模上限、资源名与产出结构）——GAMEDESIGN 已有一些原创设计（Supplies 与 Manpower/Munitions/Fuel 双系统（R6）、Spotter/OP 的放置权限、编制为上限而非固定构成（R2）），继续强化并在文档里记录"差异清单"（`docs/DIFFERENCES.md`，建议新增，不得公开引用参考作品名称）。
  3. **数值不复刻整表**：测量值 → 设计值时按 REFERENCE_MEASUREMENTS §7.2 映射并允许偏移；**仓库只存"测得的数字"，不存参考作品的截图、帧图、波形图、视频**（§1.3）；公开文档里不得出现参考作品的名称/截图。
  4. **UI 信息架构差异化**：保留"需要显示什么信息"（功能必要），但**版式、分区比例、交互节奏、转场、反馈方式**走 UI_SPEC 的 Plotline 原创系统；UI_SPEC §10 的"原创性自查清单"与"盲对照防近似检查"**每屏必做**；部署流程的步骤顺序与分组方式可以有意调整（例如先选兵种再选出生点，或合并步骤），记录差异理由。
  5. **对外沟通卫生**：营销/商店/社区**禁止**使用"X-like"、"HLL 同类"、参考作品关键词作 SEO/标签；官方描述用品类词（"大规模战术二战射击"）；不蹭对方社区。
  6. **仓库卫生**：公开代码仓库前，把所有提到参考作品名称的内部文档（REFERENCE_MEASUREMENTS、部分 GAMEDESIGN/UI_SPEC 的对标说明）**移入私有仓库/内部目录**，公开仓库只保留"品类对标"措辞；或保持整个仓库私有（H-041）。
  7. **独立创作证据**：保留设计日志（日期、决策、来源），尤其是 Loadout、UI、地图布局的"推导过程"；每个 PR 的 UI 自查清单留存。
  8. **并排审查**：公开测试前，律师（或熟悉游戏行业的顾问）做一次"并排对比审查"，列出需要进一步差异化的清单；该清单作为 M4 验收项。
- **应急预案**：收到投诉/律师函 → 立即停止对外宣传，咨询律师；按律师意见修改相似元素（优先改名称、图标、版式、兵种分类），必要时下线受影响的屏/内容；最坏情况下关闭服务。**预留 2–4 周的"表达层重做"缓冲**写入 M4 计划（Fable 审阅）。
- **对应文档**：总纲 §1、GAMEDESIGN §0.1、UI_SPEC §10、REFERENCE_MEASUREMENTS §1。

### R-32 参考作品 EULA 对录制/分析的限制

类别：法律/IP｜概率：中｜影响：中｜最晚验证：M0｜负责方：人

- **描述**：REFERENCE_MEASUREMENTS §1.3 与附录 B：参考作品用户协议对录制/分析的条款**未核实**。EULA 可能禁止：逆向/拆解（我们本来就不做）、**对游戏进行"数据挖掘/自动化测量"**、录制用于"商业竞争产品"的分析、使用游戏内容开发竞品。若有此类条款，REFERENCE_MEASUREMENTS 的方法（人工游玩录制 + 逐帧分析）可能被视为违反协议；违反的后果通常是**账号封禁**、合同层面的责任，在极端情况下作为不正当竞争案件中的不利事实。
- **触发信号**：EULA 含 "reverse engineer"、"competing product"、"record"、"analyze" 等条款；游戏更新 EULA 加严；录像会话被反作弊判定异常（封号）。
- **缓解方案**：
  1. **M0 前由人通读 EULA（H-011）并存档快照**（含版本日期）；要点交给律师（H-040）。
  2. 若 EULA 禁止录制/分析：**改用公开资料**（官方日志、公开视频、玩家社区公开描述的规则，REFERENCE_MEASUREMENTS §1.2 允许的类别），将受影响测量项的置信度记为 D，使用史实基线 + 初值 + 待调参。
  3. 所有测量在练习场/私人服务器/空服进行，不影响他人；不使用任何第三方外挂/数据挖掘产物。
  4. 录像私有存储、不上传、保留期 90 天后销毁（§1.3）。
- **应急预案**：EULA 明确禁止 → 停止自录；仅用公开视频与公开规则资料；对已录部分咨询律师是否需销毁；不影响项目继续（手感靠内部试玩 + balance-sim 调）。
- **对应文档**：REFERENCE_MEASUREMENTS §1.3、§9.2 #1、附录 B。

### R-33 历史符号（德军标志）的司法辖区限制

类别：法律/IP｜概率：中｜影响：高｜最晚验证：M0（决定默认）、上线前（律师确认）｜负责方：人（主）、执行者（落实）

- **描述**：二战游戏使用纳粹相关符号（卐字符、SS 符号、部分国徽鹰徽带卐、纳粹旗帜等）在**德国（刑法典相关条款，具体条文号以律师确认）**、奥地利、部分其它国家有展示/传播限制；存在"艺术/科学/教学/报道历史事件"等例外条款（"社会相当性"），其在**互动娱乐软件中的适用**是争议和变动的领域，**未核实**；此外，**主机/应用商店/托管服务商/支付处理方/CDN 的政策**可能比法律更严（例如违反其内容政策即下架/封停），且游戏若可从德国访问，运营者可能面对风险。"德军标志"还包括：国防军鹰徽带卐字胸徽、坦克/飞机上的卐字（后期通常只有 Balkenkreuz），购入的角色/武器/载具素材**可能自带这些符号**。简体中文 UI 不等于面向中国大陆运营：若中国大陆玩家可访问，合规要求（版号/ICP/未成年人保护）未核实，默认不面向大陆运营（H-092）。
- **触发信号**：购入素材的贴图/网格含卐字、SS 符文（贴图扫描或人工检查发现）；律师建议"不得展示"；平台/CDN 来函；社区投诉。
- **缓解方案**：
  1. **默认设计决定：整个产品不显示任何纳粹符号**（卐字、SS 闪电符文、带卐国徽鹰徽、纳粹旗帜）；德军阵营用**Balkenkreuz（铁十字/国防军十字，用于载具与飞机识别）**、中性鹰徽（无卐或空白）、阵营色/几何符号做识别——Balkenkreuz 在德国等地的法律处理**未核实**，需律师确认。**这是默认，需由人确认（H-024）。**
  2. **素材层**：在购买前检查素材预览是否含符号；入库时执行者运行"符号扫描"（人工 + 预览图/贴图人工抽查）；需要去除的符号走**D-MOD 例外（H-002）**——由人批准一种允许的处理（贴图局部遮盖/替换为中性图案；仅限去除符号，不构成"重画贴图"）。
  3. **设置项**：不提供"显示历史符号"开关（避免被视为提供违法内容的入口）；若人（在律师意见后）决定在某些地区提供，需做地理限制与年龄门槛，不属于首发范围。
  4. **文案**：UI/文案中不使用纳粹党衔/口号；阵营名称用"German Army / Wehrmacht"等中性历史称谓。
  5. 进入律师咨询议程（H-040）。
- **应急预案**：被投诉/下架 → 立即移除相关素材/文案并发布；对德国地区 IP 做地理限制（成本与可行性未核实）。
- **对应文档**：总纲 D-MOD、MAPS（德军标志不涉及）、ASSET_SHOPPING_LIST §2.2、UI_SPEC §10.3（医疗不使用红十字的同类思路）。

### R-34 真实武器/载具名称与厂商商标

类别：法律/IP｜概率：低｜影响：中｜最晚验证：M2｜负责方：人（决定）、执行者（落实）

- **描述**：游戏使用真实武器/载具名称与史实参数（总纲 §1 末条）。其中部分名称今天仍可能是**有效商标**或属于仍存续的厂商品牌（如多个枪械/载具制造商的品牌与徽标；"Jeep" 为知名商标；Thompson/Colt/Browning/Mauser/Walther 等厂商名称与标识的商标状态**未核实**）；历史上存在军火/载具厂商对游戏使用其名称/形象要求许可的先例（具体个案**未核实**）。模型贴图上的厂商标记（如枪机上的刻字、车头徽标、底盘铭牌）更直接。

### R-35 游戏对外名称与商标冲突

类别：法律/IP｜概率：中｜影响：中｜最晚验证：M0（域名）、上线前（商标检索）｜负责方：人

- **描述**：项目工作名 "Frontline" 是**极其通用的英文词**，商标冲突与可发现性（SEO）都差；同时模式名 "Frontline"、"Assault"、"Skirmish" 是模式原创命名（总纲 §1），**产品名**与模式名都叫 Frontline 会混淆。UI_SPEC §10.5 要求"对外名称、域名、社交账号与任何商业游戏无混淆可能"。域名、社交账号、OAuth 应用名、隐私政策、TLS 证书都依赖最终名称，名称不定会拖住上线前一切。
- **触发信号**：商标检索（至少美国 USPTO、欧盟 EUIPO、德国 DPMA、WIPO Global Brand Database，**可用性与检索方式未核实**）出现软件/游戏类（国际分类第 9、41 类）冲突；目标域名已被占用；社交账号名被占用。

- **应急预案**：撞名 → 改名（成本取决于改名时机：越早越低；M0 末是最后低成本窗口）；所有对外字符串走 `i18n`/配置，禁止硬编码产品名（已规定走 i18n key）。
- **对应文档**：总纲 §1、UI_SPEC §10.5、ARCHITECTURE §18.2。

### R-36 OSM ODbL 义务（share-alike）

类别：法律/IP｜概率：低｜影响：中｜最晚验证：M1｜负责方：人（决定）、执行者（实施）

- **描述**：MAPS §2.5：OSM 数据 ODbL 1.0，需署名 "© OpenStreetMap contributors"；**Produced Work**（渲染画面）仅需署名；**Derivative Database**（我们把 OSM 数据提取后合并进 `roads.geojson`/`buildings.geojson` 并**公开发布**）触发 share-alike：该衍生数据库须以 ODbL 公开。BRIEF R9 默认：接受把衍生矢量层（roads/hedgerows/buildings）按 ODbL 公开、游戏内署名。风险：①人尚未确认接受（H-004）；②**与其它数据（IGN/Etalab、瓦隆数据、历史地图描摹）混合到同一数据库时的许可证兼容性未核实**，可能"污染"；③OSM 衍生层与 `/data/maps/*` 的"其余游戏数据"混在一起，导致不清楚哪些必须公开。
- **触发信号**：矢量数据文件无法追溯来源标注；法律意见认为我们的混合库须整体 ODbL 公开；OSM 社区质疑。
- **缓解方案**：矢量层来源**分层存放**：`osm-derived/`（ODbL，独立 NOTICE）与`original/`（手绘/历史图描摹，自有许可）分开；在 `/data/maps/{id}/NOTICE` 声明；构建时 Produced Work（游戏本体）只需署名；`map-pipeline` 记录每个多边形/线的来源标记（`source: osm|hand|ign|...`）；人确认接受 ODbL 公开（H-004）；若不接受，则改为"OSM 仅作视觉参考、全部手绘"，**工时 +30–50%**（MAPS §9.1 异议 2）。
- **应急预案**：被判定须整体公开 → 按 ODbL 公开该数据库（不影响代码与素材）；不接受公开 → 重做受影响图层（手绘）。
- **对应文档**：MAPS §2.5、§9.1 异议 2、总纲 R9。

### R-37 历史航拍、地图、档案与地理数据源许可

类别：法律/IP｜概率：中｜影响：中｜最晚验证：M1｜负责方：人

- **描述**：MAPS §2 汇总的许可状态大量为"部分核实/未核实"：**瓦隆 LiDAR/DTM**（Foy 唯一高程来源）官方许可证未核实（第三方 wiki 称开放须署名）；IGN LiDAR HD/RGE ALTI 的 Etalab 2.0 来自搜索摘要，门户页抓取为空壳；**IGN "Remonter le temps"** 单张影像再利用许可未核实；**NCAP** 非研究用途按用途报价；**IWM** 标准分辨率仅私人/非商业，商业需付费授权，"捐赠是否算商业"未经法律确认（MAPS 保守不嵌入任何 IWM 影像）；**GSGS 4250** 王室版权期限未核实、扫描托管方条款未明；McMaster/UT/LoC/NARA 条目级许可需逐条检查；Copernicus DEM GLO-30 国家例外清单来源矛盾。MAPS 的"使用原则"：航拍/老照片**只作描摹参考，不作为贴图或嵌入内容**。
- **触发信号**：核实时官方元数据页显示 NC 或需授权；NARA 条目 Use Restrictions 非空；瓦隆 LiDAR 要求署名格式特殊或限制再分发；历史图被认定"描摹 = 衍生作品"。
- **缓解方案**：
  1. T-LIC 任务（MAPS §7.1）：人逐源核实原页面并**截图归档**到 `licenses/texts/`，写入 `LICENSES.md`；瓦隆 LiDAR 由人**写邮件向 SPW 确认**（联系信息来自教程摘要，**未核实**，H-072）。
  2. 严格执行"只参考、不入库"：不使用任何受限影像做贴图/嵌入；矢量以 LiDAR/OSM/现行开放数据为基础，历史图只用来**核对事实与地理配准**（事实性信息的保护通常较弱，但仍属未核实，咨询律师）。
  3. Foy 的备选：Copernicus GLO-30 + 手工微地形（质量显著下降，仅应急，MAPS §5.7）。
- **应急预案**：某数据源许可不允许 → 换源；Foy 的瓦隆数据被限制 → 降级到 GLO-30 路线或把 Foy 延后（M4 内容，不影响 M1–M3）。
- **对应文档**：MAPS §2.1–2.6、§5.7、§9.1、§9.2。

### R-38 年龄分级、暴力内容与未成年人

类别：法律/IP｜概率：中｜影响：中｜最晚验证：上线前｜负责方：人

- **描述**：游戏是高致死率战争射击，含倒地/流血/爆炸，GAP-V15 血迹贴花（"是否保留血迹也涉及年龄分级/平台政策"）。**独立网页游戏不一定强制取得 PEGI/USK/ESRB 分级**（是否需要、哪些司法辖区要求在线内容做青少年保护措施，如德国的青少年媒体保护规则，**均未核实**）；若通过 itch.io/Steam/其它商店上架，会涉及 IARC 等自评流程。涉及未成年人：GDPR 对儿童同意年龄的各国规定不同（13–16 岁，未核实）；COPPA（美国，13 岁以下，未核实）。
- **触发信号**：律师指出需做年龄门槛；上架渠道要求分级；家长/学校投诉。
- **缓解方案**：首发在启动页加**年龄确认/"成人内容声明"页面**（H-083 与律师确认文案）；ToS 规定 ≥ 16 岁（或更高，**由人在律师建议下定**）；暴力强度分档设置（血迹/肢解开关，默认保守；GAMEDESIGN 目前为低血腥写实，未设计肢解）；不收集 13 岁以下信息；不提供语音给未登录/未确认年龄用户（可选，运营设计）。
- **应急预案**：被要求分级/整改 → 按要求调整血迹等强度；极端情况下对特定地区做访问限制。
- **对应文档**：ASSET_GAPS GAP-V15、ARCHITECTURE §19.4。

### R-39 隐私法规（GDPR 等）：语音、账号、日志

类别：法律/IP｜概率：中｜影响：高｜最晚验证：上线前（M2 起收集前就要有底线）｜负责方：人（主）、执行者（落实）

- **描述**：ARCHITECTURE §19.4 的设计已做最小化：**语音不录制/不存档**（LiveKit 关闭 egress，服务器日志不含音频；举报也无语音证据）、聊天局终即弃（举报关联的前后 20 条保留 14 天）、仅存昵称/设置/基础战绩/OAuth 的 `provider_id` 哈希、IP 只短期（≤ 30 天）、客户端遥测匿名且默认关闭/首次明确同意。**但仍存在**：①面向欧洲区需 GDPR 流程（数据导出/删除端点、隐私政策、合法性基础），**文案待人定与法务审阅**；②本地存储/Cookie 同意（ePrivacy，localStorage 存 JWT 是否属需同意类别需律师确认）；③**第三方处理方**：Cloudflare、服务器厂商、Discord/Google OAuth、Anthropic API（LLM 指挥官：输入战况 JSON，不含聊天与个人数据，ARCHITECTURE §16.4）——需 DPA/披露；④跨境传输；⑤欧盟 DSA 对用户生成内容（聊天/语音）的义务（对小型服务的适用性**未核实**）；⑥未成年人（R-38）；⑦"举报无语音证据"导致无法处理语音骚扰（R-43）。
- **触发信号**：用户提交数据导出/删除请求；监管/投诉邮件；律师指出遗漏；上线前 checklist 未完成。
- **缓解方案**：
  1. 在 gateway 实现**数据导出/删除端点**（ARCHITECTURE §19.4）作为 M3 任务；隐私政策/ToS/Cookie（本地存储）说明作为 M4 前人工任务（H-082）。
  2. 数据保留策略写成代码里的常量并在**监控里验证**（过期日志被删）。
  3. 对第三方处理方做清单（`docs/PRIVACY_PROCESSORS.md`，建议新增），披露在隐私政策中。
  4. 客户端遥测**默认关闭**；开启需要显式同意；不采集 GPU 以外的硬件指纹。
  5. 运营主体与联系邮箱（含 Impressum 类要求，德国站点常见，**未核实**）：H-085。
- **应急预案**：收到合规投诉 → 按流程在法定时限内响应（具体时限由律师确认）；必要时临时关闭 OAuth/遥测/聊天存档功能。
- **对应文档**：ARCHITECTURE §14.5、§19.4、§19.2。

### R-40 "免费 + 捐赠"的商业定性与收款合规

类别：法律/IP｜概率：中｜影响：中｜最晚验证：上线前｜负责方：人

- **描述**：A1：免费游玩、接受捐赠、无付费内容。多处依赖"捐赠是否构成商业收入"：Fab Standard 的 $100,000 收入档、各 itch.io/卖家对"商用"的定义、IWM 的非商业许可、MoCap Online 的 100 万用户/US$1M 阈值；这些**都按"保守当作收入"处理**（ASSET_SHOPPING_LIST §2.1）。另外：收款平台（Ko-fi、Patreon、GitHub Sponsors、Open Collective、Stripe 等）的 KYC、税务申报（个人 vs 实体）、增值税/销售税、**"不得以捐赠换取游戏内利益"**才能保持 A1 的"无付费内容"定性（若有捐赠者特权，可能被视为销售）。
- **触发信号**：收入接近素材许可的阈值；税务/平台要求；有人要求"捐赠者专属皮肤"。
- **缓解方案**：H-086 选定捐赠渠道与主体；**原则：捐赠不换任何游戏内权益**（GAMEDESIGN 无付费内容，UI_SPEC §4.2 仅有"捐赠入口"外链）；季度检查累计收入 vs 各许可阈值；税务咨询（会计）。
- **应急预案**：触达阈值 → 升级对应许可（如 MoCap Commercial，预算入 R-21）或替换素材；若主体需注册公司，先停捐赠入口。
- **对应文档**：ASSET_SHOPPING_LIST §2.1、§7.2 #2、§7.3 #8、UI_SPEC §4.2。

## 6. 产品 / 运营风险

### R-41 玩家数不足与 bot 填充质量

类别：运营｜概率：高｜影响：高｜最晚验证：M4（公开测试）｜负责方：人（运营）、执行者（bot）

- **描述**：50v50 需要 100 人；A5 规定"真人不足由 bot 填充"，bot 是容量常态而非例外。真实情况：一款无名的免费网页游戏**很难同时聚集 100 个真人**，对局大部分是 bot；若 bot 行为质量不高（跑位呆板、卡地形、不会用载具/补给/重生点、枪法不合理），整体体验崩塌，玩家会觉得"空"；若为了好看而提高 bot 难度，则"被 bot 虐"。bot 同时消耗服务器 CPU（R-06）。
- **触发信号**：M1 的 20 名真人测试中，玩家主观评价"bot 明显"比例 > 60%；对局平均真人数 < 15%；bot 卡死/重复同一路径的事件率；新玩家次日留存 < 10%（**阈值为估计**）。
- **缓解方案**：
  1. 产品层面：**Skirmish（16v16，GAMEDESIGN §3.5）作为低人数默认模式**，Frontline 100 人作为"活动局"；按在线人数自动选择模式；允许"固定开局时间"（如每晚 20:00 的"大战役"）集中人流。
  2. bot 设计：分层（指挥官 → 小队长 → 士兵）、行为树 + 效用 AI（总纲 §3）；**bot 与真人同路径输入**（ARCHITECTURE A5），保证与真人遵守同样规则；难度参数（GAMEDESIGN §20.6）可调；bot 命名/标识诚实标注（"BOT"），玩家可见。
  3. 度量：`balance-sim`（无渲染 bot 对战）与"图灵式盲测"：把 bot 与真人录像混合让测试者分辨。
  4. 社区：公开测试前建立 Discord，招募固定测试员；与现有 WW2 社区/内容创作者合作（不蹭对方品牌，R-31）。
  5. 避免过早开放：先小规模邀请制，把"真人密度"作为开放指标。
- **应急预案**：真人持续不足 → 缩小单局规模（Skirmish 为主）、合并服务器、关闭多余机房；把定位调整为"可与朋友开房的 bot 战术游戏"（私房/自建房，ARCHITECTURE 目前未设计，需追加设计）。
- **对应文档**：总纲 A5、GAMEDESIGN §3.5、§4.7、§20、ARCHITECTURE §16。

### R-42 作弊（浏览器端不可防部分）

类别：运营｜概率：高｜影响：中｜最晚验证：M4｜负责方：执行者（检测）、人（处罚决策）

- **描述**：浏览器环境**无法做内核级反作弊**，客户端完全不可信（ARCHITECTURE §15.4、§20 #8）；自瞄只能靠统计检测，宏/脚本（压枪、自动开火）、透视（AOI 已缓解，不下发视野外远距离敌人的精确数据）、改变参数/加速（服务器校验移动速度/加速度/射速/弹药）、DevTools 修改、第三方脚本、延迟作弊（人为拔网线）。匿名游客（A8）使得**封号几乎无成本**：封后换设备/清缓存即可回来。
- **触发信号**：`suspicion_score` 分布右尾增长；举报量/局 > 阈值；某账号爆头率/命中率统计异常；社区热帖"作弊泛滥"。
- **缓解方案**：
  1. 服务器权威 + 校验清单（ARCHITECTURE §15.1）；AOI 作为信息控制（§15.2）；命中回溯合理性检查（上限 250 ms，§6.7）。
  2. 统计检测（§15.3）+ 举报 + 管理员工具（GAMEDESIGN §19.6）；**检测只做"告警 + 人工复核"，不自动永久封号**（防误封）。
  3. 提高作弊成本：**可选要求 OAuth 账号**（Discord/Google）才能进"推荐服务器"或开启语音/聊天；游客限制在"Skirmish/练习"（需人决定，H-063，与 A8 默认"匿名游客"冲突，需明示取舍）。
  4. 使用指纹式 ban（IP + 账号 + 设备 token）的隐私影响需评估（R-39）。
  5. **对外诚实**：在 ToS/FAQ 里说明"浏览器游戏无法做到 PC 级反作弊"。
- **应急预案**：作弊严重 → 开启"仅登录账号可玩"、提高举报权重、引入"信任等级匹配"（新账号只能与新账号同局）；极端情况下限制服务器为邀请制。
- **对应文档**：ARCHITECTURE §15、§19.3、GAMEDESIGN §19.5–19.6、§20 #8。

### R-43 语音/聊天滥用与内容审核

类别：运营｜概率：高｜影响：中｜最晚验证：上线前｜负责方：人

- **描述**：语音与文字聊天会产生辱骂、仇恨言论、纳粹/极端主义言论（二战主题更容易吸引）、骚扰；**设计决定语音不录制**（R-39），因此**无语音证据**，举报只依赖文字/行为/统计（ARCHITECTURE §19.4 明确告知用户）——这使语音骚扰难以处理。1 名人类负责人没有审核人力（R-46）。DSA 等对 UGC 平台的义务**未核实**。
- **触发信号**：举报量/日 > 人力可处理量；社区帖子投诉；出现严重事件（骚扰未成年人、极端言论外传）。
- **缓解方案**：
  1. 制定**社区守则与处罚阶梯**（H-075）：警告/禁言/踢出/封禁（临时/永久）与申诉流程；对外公示。
  2. 工具：聊天速率限制与重复检测、可选敏感词表（词表按语言，待人定，ARCHITECTURE §19.3）、玩家一键屏蔽/静音、"仅小队语音"默认可选。
  3. 招募志愿管理员（版主）与权限分级；审计日志（保留 1 年，§18.4）。
  4. 语音保护：默认关闭近距离语音，新账号需先阅读守则；是否要求登录才能开麦（见 R-42）。
  5. 评估"短时滚动录音缓冲仅在举报时上传"的方案（会改变 R-39 的隐私设计，**必须经律师确认**，默认不做）。
- **应急预案**：事件发生 → 立即禁用语音（服务器端开关）、封禁涉事账号、发布公告；严重时暂停公开服务器。
- **对应文档**：ARCHITECTURE §14、§19.3–19.4、GAMEDESIGN §16。

### R-44 服务器与带宽成本

类别：运营｜概率：中｜影响：中｜最晚验证：M2｜负责方：人

- **描述**：ARCHITECTURE §18.1：2 台主机 × 2 局 = 4 局 × 100 = 400 并发上限（含 bot）；单局 ≈ 11 Mbps（含语音转发），4 局 ≈ 45 Mbps 均值；**具体价格未核实**（文档不给）。另有：R2 + CDN（出口流量费、请求费未核实；一般声称 R2 无出口费，**未核实**）、首图 150 MB × 新玩家数的流量（R-13）、监控机、域名、LiveKit、LLM 指挥官成本（R-47）。A1 无收入。
- **触发信号**：月账单 > 预算 20%；单局 CPU 超预期导致需要更多主机；CDN 出口流量突增（病毒式传播/被爬）。
- **缓解方案**：H-020 设月度预算上限与告警；先精简档（1 台对局 + gateway/LiveKit 合并）；按需启停：空服务器自动缩容/关机；静态资源全走 R2 + CDN 且设缓存策略；监控 `server_players`，低于阈值合并局；M2 实测后给出"每并发玩家成本"。
- **应急预案**：成本不可持续 → 限制并发（排队）、缩短开放时间（只在活动时段开服）、募捐/关闭部分功能；若必须，暂停服务。
- **对应文档**：ARCHITECTURE §18.1、总纲 A5–A6。

### R-45 DDoS

类别：运营｜概率：中｜影响：中｜最晚验证：上线前｜负责方：人（选供应商）、执行者（限速）

- **描述**：游戏服务器 UDP（WebTransport/QUIC）直接暴露源 IP；常见 CDN/代理对 UDP/HTTP3 游戏流量的保护程度不同，**能力未核实**（ARCHITECTURE §19.3 已写"由主机防火墙/云厂商 DDoS 防护兜底（能力未核实）"）；免费游戏与竞争/恶作剧容易招来 DDoS；gateway（HTTP）可置于 CDN 后。
- **触发信号**：丢包率突增、`net_packet_loss_ratio` 异常、QUIC 初始包洪泛、日志中同一 /24 段海量握手。
- **缓解方案**：选择**带 DDoS 防护的主机商**（H-016、H-087 的选型标准之一，具体厂商防护能力未核实，需人在合同前核实）；每 IP 并发连接上限 4、握手 5 s 超时（ARCHITECTURE §19.1）；源 IP 不公开（gateway 做匹配、服务器地址只对匹配结果可见）；WS 兜底可通过 CDN 代理（是否允许游戏流量走 CDN 的条款**未核实**）；预案化"换 IP"。
- **应急预案**：被攻击 → 切换备用 IP/机房、启用供应商"清洗/黑洞"、暂停公开服务器并公告。
- **对应文档**：ARCHITECTURE §19.1、§19.3。

### R-46 单人负责人的 bus factor

类别：运营｜概率：高｜影响：高｜最晚验证：M2｜负责方：人

- **描述**：A2：1 名人类负责人 + AI 执行者。所有账号（域名、云、支付、素材商店、OAuth、Fab）、所有法律/付款决定、所有审美拍板、运营审核都在一个人身上。该人生病/出差/倦怠/失联，项目停滞；密钥与账号无备份则**无法恢复**；AI 执行者的可用性与模型价格/政策也是单点（供应商变更、API 限额）。
- **触发信号**：NEEDS_HUMAN 事项平均响应时间 > 3 天；人连续 2 周无提交；账号无备份人；某次密码丢失/MFA 设备丢失。
- **缓解方案**：
  1. **应急联系人/备份管理员**（H-065）：至少一名可信第三人持有"紧急恢复信封"（密码管理器的恢复密钥、域名/云账号的恢复方式）；写入 `docs/OPS_RUNBOOK.md`（建议新增）。
  2. 全部凭据放**团队密码管理器**，MFA 恢复码离线保管；不使用个人邮箱作为唯一联系人，用项目邮箱 + 转发给备份人。
  3. 所有流程文档化：部署、回滚、证书续期、封禁处理（Runbook）；执行者定期更新。
  4. 降低对人的依赖：把"需要人"的事项集中到 NEEDS_HUMAN，批量处理（每周固定时段）；自动化可自动化的运维。
  5. 在 M2 之后评估把"运营/审核"外包给志愿者版主。
- **应急预案**：负责人长期不可用 → 备份人关停对外写入（只读/暂停服务）、保留数据；项目暂停并公告；代码仓库与文档保持可交接状态。
- **对应文档**：总纲 A2、ARCHITECTURE §18。

### R-47 LLM 指挥官的成本、可用性与安全

类别：运营｜概率：中｜影响：低｜最晚验证：M3｜负责方：执行者

- **描述**：可选功能（每队 1 个 LLM 指挥官，ARCHITECTURE §16.4）。风险：①成本——BRIEF R4 已把决策间隔改为 **60 s**，每局上限 0.5 美元；**模型价格未核实**，实现前按官方价格重算。【估算】按 4 局并发、每局 75 分钟计，一天约 77 局，若每局触顶 $0.5，则约 $38/天、≈ $1,150/月，是**上限情景**，非预测；若指挥官始终关闭则为 0。②可用性：API 限流/宕机，规则指挥官热备已设计；③提示注入：设计已规定输入只含该队可见信息、不含聊天内容，输出为受限枚举并经校验；④数据外发：结构化战况 JSON，不含个人信息（但需在隐私政策披露第三方处理，R-39）；⑤ARCHITECTURE §16.4 正文仍写 45 s，与 BRIEF R4 的 60 s 不一致（见 R-51）。
- **触发信号**：`llm_cost_usd_total`/局 > 0.45（§18.3 告警线）；`llm_fallback_total` 比例 > 20%；账单月度超预算。
- **缓解方案**：默认**关闭**，仅在真人少于阈值/活动场启用；全局月度预算硬上限（H-073，在 Anthropic 控制台设置支出上限）；成本控制器（90% 拉长间隔，100% 回退）已设计，实现后用实际用量校准；API key 仅在服务器环境变量，不进日志（R-55）。
- **应急预案**：成本/可用性问题 → 关闭 LLM，规则指挥官接管（热备）；功能砍掉不影响核心。
- **对应文档**：ARCHITECTURE §16.4、§20 #13、总纲 R4。

## 7. 流程风险

### R-48 AI 执行者偏离计划/架构漂移

类别：流程｜概率：高｜影响：高｜最晚验证：M0｜负责方：Fable 审阅（主）、人

- **描述**：计划将交给 Sonnet 逐任务执行，周期长、上下文有限。典型漂移：①悄悄换技术栈（如因为遇到困难改用 Three.js、改成 TS 服务器）；②引入未批准的依赖；③为了过测试而改测试/放宽阈值；④局部"优化"导致模块边界被破坏（违反 ARCHITECTURE §4.5 禁止依赖速查表）；⑤把 `/data` 数值硬编码进代码（GAMEDESIGN §0.2 明确 JSON 是真源）；⑥忘记约束（对标红线：不得出现参考作品名称、不拆包）。
- **触发信号**：PR 中出现不在任务文件列出的新依赖/新目录；`cargo deny`/依赖图检查失败；架构依赖方向检查（§4.2）违规；任务回报中出现"为简化起见改为……"；`/data` 与代码常量重复。
- **缓解方案**：
  1. **任务文件模板**：必含"引用章节"、"允许改动的路径"、"禁止事项"、"验收标准（可执行的命令/数字）"、"不得改动的文档"；任务文件之外的改动视为越界。
  2. **架构护栏进 CI**：依赖方向检查（`crates/*` 之间）、禁止依赖速查表自动检查、`cargo deny`、体积门禁、数据 schema 校验、禁词扫描（参考作品名称不得出现在 `/client`、`/data`、对外字符串）。
  3. **ADR（架构决策记录）**：任何偏离计划的改动必须先提交 ADR 草稿（`docs/adr/NNN-*.md`），由人/Fable 审批后才可合并。
  4. **里程碑审阅（Fable）**：每个里程碑末做"计划-实现对照"，抽查 3–5 个任务的 PR。
  5. 执行者启动每个任务前重读相关文档章节；任务回报格式固定，包含"偏离清单（若无写无）"。
- **应急预案**：发现漂移 → 冻结该方向，回滚到最近一致提交；写事故记录（原因、修复、护栏补强）；必要时把任务粒度缩小（R-49）。
- **对应文档**：ARCHITECTURE §4、§17.5、总纲 §0/§4。

### R-49 任务粒度过大

类别：流程｜概率：高｜影响：中｜最晚验证：M0｜负责方：Fable 审阅（主）、执行者

- **描述**：像"实现 CDLOD 地形"、"实现网络同步"、"实现载具"这类任务对单次执行者会话过大，产出不可审阅、中途失败、返工昂贵；也容易引发 R-50（软通过）。
- **触发信号**：单任务的预计改动 > 800 行有效代码或 > 10 个文件；任务运行 > 1 个会话仍未有可演示的中间产物；验收标准里有"基本可用"之类词。
- **缓解方案**：任务文件必须是**可在一个会话内完成、产出可独立验证**的切片；每个任务有"一条命令验证 + 一个数字"；大特性拆成"骨架 → 数据 → 行为 → 压测 → 文档回写"链；任务文件由 Fable 抽审粒度（里程碑开始前的任务评审）。
- **应急预案**：发现粒度过大 → 暂停、拆分、重新编号（任务编号 `M{n}-{三位序号}-{slug}`，拆分用新编号，旧任务标记 superseded）。
- **对应文档**：总纲 §5（任务编号格式）。

### R-50 验收标准被"软通过"

类别：流程｜概率：高｜影响：高｜最晚验证：M0｜负责方：Fable 审阅（主）

- **描述**：AI 执行者倾向于报告"已完成"：用 mock 绕过真实网络/渲染、只在好情形下测、用估算值冒充实测值、跳过性能门槛、把 TODO 留着却标 done、测试通过但与需求不符、截图只截好看的角度。ARCHITECTURE §20 #14 已指出"估算值未经实测"，这是软通过的重灾区。
- **触发信号**：回报里"约"、"应该"、"预计"但没有数据；验收证据缺失（无日志/无截图/无基准输出）；性能结论没有硬件型号；测试里大量 `mock`/`skip`；CI 通过但有 `#[ignore]`/`.skip` 新增。
- **缓解方案**：
  1. **验收证据清单**（所有任务强制）：命令输出片段、基准数字（含硬件型号与浏览器版本）、固定机位截图、日志文件路径；缺证据则任务不得标 done。
  2. 对关键验收项设"**反例测试**"（故意制造失败条件，确认测试会失败），防止恒真测试。
  3. CI 禁止新增 `#[ignore]`/`.skip` 而无引用 ADR；覆盖率不作为唯一标准。
  4. Fable 审阅在里程碑末**独立复跑**关键基准（M0 的 5 条退出条件、M2 的 100 人压测），不使用执行者的报告值。
  5. "估算 → 实测"对照表（见 R-18）。
- **应急预案**：发现软通过 → 任务重开；该里程碑的验收需重新做一遍；在 ADR/事故记录里写明并补护栏。
- **对应文档**：ARCHITECTURE §17、§20、§20.1。

- **描述**：多文档由不同作者并行撰写、总纲几经追加（§3b、§3c 裁定优先）。已知或疑似不一致（**审阅时核对，若并行编辑已修复则忽略**）：

### R-52 史实参数未复核（BRIEF R8）

类别：流程｜概率：高｜影响：低｜最晚验证：M1｜负责方：执行者（复核）、人（抽样）

- **描述**：GAMEDESIGN §0.4：武器与载具的口径、弹容量、理论射速、初速、乘员、装甲厚度**出自记忆、未联网逐项复核**，不同来源对同一参数常有 ±5–15% 差异；穿深是"游戏标称值"。R8 要求专门任务按 REFERENCE_MEASUREMENTS §6 的来源逐项复核，**复核完成前 `/data` 状态一律为 `initial`**。REFERENCE_MEASUREMENTS 附录 B：TM 9-1275、TM 9-2200 在线链接未找到；德军 HDv/Merkblatt、Hogg 版次、博物馆条目未检索具体链接。
- **触发信号**：史实爱好者指出明显错误；`/data` 中仍有 `initial` 状态的参数在 M1 之后；`source` 字段为空。
- **缓解方案**：M1 内排一个"史实复核"任务：逐字段填 `source`、`status: verified|initial`，引用 §6.2 权威来源（TM 系列、Green Books、博物馆资料）；游戏性取舍（压缩射程等）单独标注 `gameplay_override: true` 并给出理由；人抽样复核 ≥ 10%（REFERENCE_MEASUREMENTS §9.2 #11）。
- **应急预案**：复核发现大偏差 → 以可靠来源为准修改并通过平衡模拟回归；对外不宣称"史实精确"，只称"史实参考"。
- **对应文档**：GAMEDESIGN §0.4、REFERENCE_MEASUREMENTS §6、附录 B、总纲 R8。

### R-53 对标测量迟迟不做，手感无依据

类别：流程｜概率：高｜影响：中｜最晚验证：M0（首批）｜负责方：人（录制）、执行者（分析）

- **描述**：REFERENCE_MEASUREMENTS §9.1 的批次（批 M0 需要步枪射击 W 系列与基础移动 M 系列、生存 H-01–H-03；批 M1 更多）**依赖人合法获取参考作品、准备 ≥ 120 fps 录制设备、人工游玩录制、辅助者**。这些全是人工且耗时；若迟迟不做，GAMEDESIGN 里 53 项 `T-xx` 待调参只能用"自拟初值"，M0 的"射击/移动能玩"没有基准，后期再改会引发大量返工（R-48、R-57）。

- **对应文档**：REFERENCE_MEASUREMENTS §4、§7、§9、GAMEDESIGN §21。

### R-54 人类阻塞：NEEDS_HUMAN 事项积压

类别：流程｜概率：高｜影响：高｜最晚验证：M0｜负责方：人

- **描述**：项目的关键路径上有**大量只有人能做的事**：决定、付款、注册账号、法律咨询、录制测量、审美定稿、运维（见 `docs/NEEDS_HUMAN.md` 全表，约 70 项）。A2 只有 1 名人类；AI 执行者可以灰盒占位绕开部分素材阻塞，但**无法绕开**账号、付款、法律、录制。积压的结果：执行者空转、里程碑延期、或执行者被迫自行假设（越界，R-48）。
- **触发信号**：NEEDS_HUMAN 中状态仍为 `[ ] 待办` 且"阻塞里程碑"为当前里程碑的项 > 5；某项待办超过其"最晚时点"；执行者回报"因 H-xxx 未决而采用默认假设"的次数上升。
- **缓解方案**：
  1. NEEDS_HUMAN 顶部"本周最该做的 5 件事"每周更新；每周固定一个时段（如 2 小时）批量处理。
  2. 每项都给**默认假设**（NEEDS_HUMAN 各项"默认假设"栏），人不响应时执行者按默认继续并在回报里标注（降低阻塞；但法律/付款类**没有默认**，只能等人）。
  3. 能并行的事先并行：邮件先发、律师先约、账号先注册——它们有**外部等待时间**。
  4. 优先级：先做会产生外部等待的事项（卖家回复、律师预约、开户审核、域名/证书传播）。
  5. Fable 审阅在每个里程碑开始前列出"该里程碑的人类阻塞项"，人确认完成或接受默认。
- **应急预案**：人手不够 → 缩小范围（R-57）；将可外包的事项（制图描摹、录像分析、版主）外包或找志愿者；允许把部分里程碑目标推迟。
- **对应文档**：`docs/NEEDS_HUMAN.md`。

### R-55 密钥/凭据泄露进仓库或日志

类别：流程｜概率：低｜影响：高｜最晚验证：M0｜负责方：执行者（防护）、人（保管）

- **描述**：执行者要部署、调用 API、签发 token；多个密钥（Anthropic API key、LiveKit key/secret、Cloudflare token、OAuth client secret、JWT 签名私钥、服务器 SSH key）。泄露后果：被盗刷（LLM API 费用）、冒充签发 join ticket、数据外泄。AI 执行者可能在日志、示例、测试夹具里不小心写入密钥；`.env` 误提交。
- **触发信号**：`gitleaks`/GitHub secret scanning 告警；日志中出现形似密钥的字符串；账号异常登录/费用突增。
- **缓解方案**：NEEDS_HUMAN §10 的"密钥与凭据清单"只列名称与用途，**从不进入仓库**；仓库只放 `.env.example`（只有变量名）；CI 加 `gitleaks`/secret scan；pre-commit hook；密钥通过 CI Secrets/服务器环境变量/密钥存储注入；日志脱敏（ARCHITECTURE §16.4 已要求 API key 不进日志）；每个密钥**最小权限**与**独立可轮换**；JWT 签名私钥与 LiveKit secret 仅 gateway/服务器持有（§19.2）。
- **应急预案**：泄露 → 立即吊销并轮换（runbook 步骤）；检查费用与日志；强制所有 token 失效（JWT 签名密钥轮换）；如已进 git 历史，重写历史并视为已泄露。
- **对应文档**：ARCHITECTURE §19.2、§19.5、NEEDS_HUMAN §10。

### R-56 CI 额度与构建时长（Rust + WASM + 视觉回归）

类别：流程｜概率：中｜影响：低｜最晚验证：M1｜负责方：执行者、人（账号/额度）

- **描述**：ARCHITECTURE §17.5 CI 用 GitHub Actions：Rust 全量构建、WASM 构建、`cargo test`、`vitest`、Playwright 视觉回归（Chromium 带 GPU？CI 通常无 GPU，WebGPU 需软件渲染，**可行性未核实**）、`headless-client` 压测不适合放普通 CI。免费额度分钟数与并发有限（**额度未核实**）。
- **触发信号**：CI 单次 > 20 分钟；月度分钟用尽；视觉回归在无 GPU 的 runner 上不稳定（软件渲染差异）。
- **缓解方案**：缓存（sccache/Cargo、npm）；分层 CI（快速检查每次 PR，完整视觉回归夜间/里程碑）；视觉回归用固定软件渲染后端 + 容差；压测放自托管 runner 或手动触发；人评估是否需要付费额度或自托管 runner（H-014）。
- **应急预案**：超额度 → 降低频率、自托管 runner（一台廉价机）、减少矩阵。
- **对应文档**：ARCHITECTURE §17.4–17.5。

### R-57 范围蔓延（14 兵种、载具、3 张图、两种语言）

类别：流程｜概率：高｜影响：高｜最晚验证：M1｜负责方：Fable 审阅（主）、人（砍范围决定）

- **描述**：计划范围非常大：14 个兵种、多种载具（含带内饰坦克）、火炮、Assault/Frontline/Skirmish 三种模式、指挥官能力体系、3 张 2048 m 地图（每张大量人工）、语音（LiveKit）、LLM 指挥官、bot 三层 AI、UI 数十屏、中英双语、无障碍、辅助功能。1 名人 + AI 做这些，而 M1 才是"垂直切片"，M4 才公开测试，**很可能整体时长远超预期**；每增加一个特性，R-06、R-13、R-21、R-24、R-54 都被放大。
- **触发信号**：里程碑实际用时 > 计划 1.5 倍；M1 验收时仍有"待补"的核心功能；新增需求（"顺便加个……"）出现在任务队列。
- **缓解方案**：
  1. **冻结范围表**（`docs/SCOPE.md`，建议新增）：每个里程碑的"必须/应该/可以砍"三级；砍点预先约定：**LLM 指挥官、TAAU、近距离语音、Skirmish 之外的第三模式、冬季角色、Foy 地图**列为可砍（Backlog）。
  2. 里程碑末 Fable 审阅做"范围体检"：实际完成度与剩余量的燃尽图。
  3. 新需求必须先替换而非追加（同等工作量的旧项移出）。
- **应急预案**：延期超过 1.5 倍 → 触发范围重谈：砍 Omaha/Foy 其一（M4 缩为单图公开测试）、砍载具种类、砍语音；以"小而完整"的公开测试替代"全"。
- **对应文档**：总纲 §5、GAMEDESIGN §1、§5。
