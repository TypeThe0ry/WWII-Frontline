# REFERENCE_MEASUREMENTS —— 手感对标测量套件

> 状态：规划文档（本阶段不写实现代码）。文档版本 0.1，起草日期 2026-11-17。
> 本文档定义"手感对标套件"：**测什么、怎么测、怎么记录、怎么用来调参**。
> 所有"测量值"栏当前一律为 `待测`。**本文档不含任何实测数值**；凡出现的数字均为方法参数（帧率、重复次数、容限等），不是参考作品的数据。

## 1. 目的、合规边界与录像使用说明

### 1.1 目的

Frontline 的手感目标是"让熟悉同品类（参考作品：Hell Let Loose，下称 HLL）的玩家上手不觉得陌生"。手感由大量**时序与幅度**数字决定（射速、开镜时间、后坐、移动速度、压制强度等）。这些数字没有公开的权威表，需要通过**黑盒观测**得到近似值，再作为 `/data` 中游戏性数值的**校准依据**。

本套件产出三类东西：

1. **一份测量清单**（§4）：每一项有 ID、方法、单位、对应的 `/data` 字段。
2. **一套可重复的采集与分析流程**（§2、§3）：任何执行者照做可得到同样结果。
3. **一条调参闭环**（§7）：测量值 → `/data` → 用同一方法复测我方游戏 → 误差容限 → 自动化回归。

### 1.2 合规边界（硬约束）

**允许（黑盒观测）：**

- 人工游玩参考作品，用屏幕录制软件录下**自己的游戏画面与游戏音频**（用于内部时序分析）。
- 观看并分析**公开发布**的游戏视频（官方预告、玩家公开上传的视频），仅用于读取时序/距离/幅度。
- 阅读**官方更新日志、官方开发日志**，以及**玩家 wiki / 社区公开文档**中陈述的规则与数值事实。
- 在游戏自带的练习场 / 自建私人服务器 / 空服中，按 §2.3 搭建可重复的测量场景。
- 仅使用**游戏本身对玩家可见的 UI 与画面**读取信息（如弹药计数、地图网格、指南针刻度）。

**禁止（任何情况下都不得做，包括"只是看看"）：**

- 反编译、反汇编、拆包、解包游戏资源、读取/修改游戏内存、调试器附加。
- 抓包、协议解析、中间人、伪造或重放网络流量。
- 提取、转存、重新编码游戏的模型、贴图、动画、音效、音乐、语音、字体、图标。
- 使用第三方"数据挖掘"工具产出的、源自上述手段的数值表（即使它们公开在网上，也**不得**作为本套件的数据来源；遇到来源不明的"数据表"一律不采信）。
- 在对战服务器上妨碍他人、使用外挂/脚本辅助。测量必须在练习场、自建/空服或不影响他人的位置进行。
- 在我方仓库、游戏、素材、文案中使用参考作品的名称、商标、图标、配色、字体、文案、地图布局。

**表达层原创**：我们对标的是"规则、时序、信息架构"（显示什么、怎么交互）。名称、图标、配色、字体、版式、文案、地图布局、能力命名必须原创（见规划总纲 §1）。

> 若某项测量只能靠禁止手段才能得到，则**放弃该项**，改用"史实基线（§6）+ 初值 + 待调参"，并在 §4 该行置信度记为 `D`（见 §4.0）。

### 1.3 录像的版权与使用说明

- 录像文件**仅供内部逐帧分析**，不入库（不提交到 git）、不上传到公共平台、不转发给第三方、不用于任何宣传。
- 录像存放在人负责人指定的**私有离线存储**（本地加密盘或私有对象存储桶，访问仅限项目成员）。仓库的 `.gitignore` 必须忽略 `/assets/incoming/ref-captures/`（若放在本地）；任何 CI 都不得拉取录像。
- **仓库里只存"测得的数字"**：即 §8 的记录文件（Markdown/CSV）、分析脚本，以及我们自己游戏的录像分析结果。**不存**参考作品的截图、帧图、波形图原图、视频片段。需要在文档里说明某个现象时，用文字描述 + 数字，不贴图。
- 若需要对外说明依据（如开发日志、博客），只引用"我们测得的数字与方法"，不展示参考作品画面。
- 录像保留期：对应的 `/data` 数值通过回归验收后 90 天，由人负责人决定销毁或继续保留（待人确认）。
- 参考作品的用户协议可能对录制/分析有条款，**未核实**；动手前由人负责人通读其 EULA/用户协议，如有禁止录制或限制分析的条款，须按条款调整（见 §9 行动项）。

## 2. 采集规范

### 2.1 录制设置

| 项 | 要求 | 说明 |
|---|---|---|
| 采集帧率 | **≥ 120 fps（目标 240 fps）** | 时间不确定度 = ±1 帧 = ±8.3 ms@120 fps、±4.2 ms@240 fps。游戏自身渲染帧率必须**稳定 ≥ 采集帧率**，否则录像里会出现重复帧；不达标时降画质，不要降采集帧率 |
| 分辨率 | 1920×1080（原生渲染，不开动态分辨率/超分） | 像素标定（§3.4）依赖固定分辨率 |
| 码率 | 视频 ≥ 80 Mbps（NVENC/CQP 低值，或无损/近无损编码，如 CQP 12–16） | 码率不足会产生块效应，影响清晰度指标（§3.7）和边缘检测 |
| 编码格式 | MKV 容器（崩溃不丢文件）；录完无损转封装（`-c copy`）为 MP4 备份 | 不要二次有损转码 |
| 音频 | 游戏音频**单独一轨**，48 kHz、PCM 或 ≥ 256 kbps AAC；**关闭麦克风、关闭语音聊天、关闭背景音乐/环境音（若游戏提供滑块）** | 用于 §3.3 波形法。同时录一条"游戏音+麦克风"的对拍轨不是必须的 |
| 垂直同步 | 关闭 V-Sync，使用帧率上限 = 采集帧率的整数倍或等于采集帧率；若无法稳定，则开启 V-Sync 并选显示器刷新率 ≥ 采集帧率 | 以录像为准，不以游戏 FPS 计数器为准 |
| 动态模糊 | **关闭**（必须） | 否则速度/后坐测量失真 |
| 景深、镜头光晕、屏幕抖动/镜头晃动选项 | 能关则关；**压制效果测量（§4.5）例外**：压制的屏幕效果要**保持默认**，只关动态模糊 | 压制测量要记录"默认设置下的效果" |
| FOV | **固定**；记录游戏内 FOV 设置值（或"不可调"），整个测量批次不得变动 | FOV 标定见 §3.5 |
| HUD | 保持默认；不得隐藏弹药/指南针/地图 | 它们是读数来源 |
| 鼠标灵敏度/加速度 | 关闭鼠标加速；记录灵敏度（DPI × 游戏内数值）。**需要匀速转动时用"鼠标撞击桌边/固定距离拖动"并在 §3.5 标定转动速率**，不要凭手感 | |
| 录制软件 | OBS Studio（开源、免费）或 NVIDIA/AMD 自带录制；记录软件版本 | 录制软件的"时间戳叠加"不可用；时间一律从帧号换算 |
| 屏幕显示延迟 | 不影响录像内相对时序。**输入延迟类测量（如"点击到枪响"）如需，另用外部 240 fps 手机/相机拍摄屏幕+键盘**，在 §4 备注 | 默认不测输入延迟，只测"事件间相对时序" |

**必须记录的元数据**（写入 §8 记录模板头部）：

- 参考作品**游戏版本号/构建号**（从主菜单或启动器读取）、**测量日期**（YYYY-MM-DD）、测量者、录制软件与版本、采集帧率、分辨率、游戏内 FOV、帧时间不确定度（±1 帧对应毫秒数）。
- 游戏更新后，**旧测量标记为 `stale`**（保留，不覆盖）；重测须新建一行并带新版本号。

### 2.2 时钟与帧号约定

- **时间零点**：选"可识别的第一帧事件"，如"鼠标左键按下导致枪口火光首次出现的帧"。同一类测量每次都用同一类事件，避免系统偏差。
- 帧号 `n` 从视频第 0 帧起；`t = n / fps`。区间 `Δt = (n2 - n1) / fps`，**不确定度为 ±1 帧**（起止各 ±0.5 帧，保守合并取 ±1 帧）。
- 先用 `ffprobe` 校验视频实际为**恒定帧率**（`avg_frame_rate == r_frame_rate`），出现可变帧率（VFR）的录像必须丢弃重录。

### 2.3 场景搭建方法（可重复）

目标：任何人在任何一天都能搭出**同一场景**。每个场景写入 §8 记录头的"场景编号"。

通用原则：

1. **固定出生/站位**：每次从同一点开始（如"练习场出生点 → 沿某地面标线走 N 步"）；用地图网格坐标或明显地物作标记，并在记录里写明。
2. **平坦地面**：测速度/射击选水平地面，避免坡度。
3. **已知尺寸参照物**：场景中至少有一个已知尺寸物体（如车辆长度需先用**官方公开资料**或自测像素标定求出——**不得读取游戏文件**；优先使用游戏**地图网格**（如每格 100 m 一类的可见网格）、**指南针刻度**、**标尺类 UI**）。
4. **靶标**：用练习场固定靶/静止友军载具/固定建筑。距离读数用地图网格 + 像素标定交叉验证（§3.4）。
5. **避免干扰**：自建/私人/空服；无他人；固定天气与时间（若可调）。
6. **每次测量前后各录 5 s 空白**（静止画面），便于校时与噪声估计。

**场景清单**（编号用于 §4 引用）：

| 场景 | 内容 | 用途 |
|---|---|---|
| S-RANGE | 练习场/空服平地；沿一条直线在 50/100/150/200/250/300 m 处放置可识别靶标（或用远处固定地物，距离由地图网格量得） | 弹道、下坠、扩散、枪声距离 |
| S-FIELD | 平坦开阔地，地图网格可见，有已知两点距离 ≥ 200 m 的直线 | 移动速度、加减速 |
| S-OBST | 低/中/高矮墙若干（高度由像素标定求） | 翻越、跳跃高度 |
| S-STAIR-FALL | 可控高度的坠落点（建筑/土坡/悬崖）若干 | 坠落伤害高度 |
| S-DUMMY | 自建/私人服务器中的第二个账号（"队友"）在固定距离做靶、被救、被击倒 | 致死发数、倒地、救起 |
| S-VEH | 空旷平地 + 直线道路；载具出生点 | 载具速度/转向/炮塔 |
| S-ARTY | 火炮位 + 观测点；地图网格可见 | 飞行时间-距离表、散布 |
| S-UI | 默认部署/地图界面 | UI 时序 |
| S-AUDIO | 平地，沿直线逐步后退（固定步长）；第二账号在固定距离开火 | 枪声/脚步可闻距离 |

> 需要"第二个账号"的场景（S-DUMMY、S-AUDIO）由人负责人协调（见 §9 行动项）。

### 2.4 命名规范

文件名：

```
{项目ID}_{版本}_{日期}_{场景}_{序号}.{ext}
示例（格式示例，非真实数据）：W-01_v0.0.0_2026-01-01_S-RANGE_r03.mkv
```

- `项目ID` = §4 中的测量项 ID（如 `W-01`）。
- `版本` = 参考作品构建号（如无法获取则 `unk` 并在记录里写明）。
- `r{序号}` = 第几次重复（两位或三位数字）。
- 抽帧目录：`frames/{同上基名}/%06d.png`。
- 记录文件：`measurements/{ID}.md`（详细记录），汇总 CSV：`measurements/summary.csv`（§8）。
- **仓库只收** `measurements/` 下的文本记录，**不收**任何 `.mkv/.mp4/.png/.wav`。建议仓库路径 `docs/measurements/`（见 §9 待人确认）。

### 2.5 重复次数与统计方法

- **每个测量项至少重复 5 次**（`n ≥ 5`）；对**噪声大**的项（后坐、扩散、散布、压制）建议 `n ≥ 10`（某些需要 `n ≥ 20` 才能画分布，见 §4 备注）。
- 每次重复独立开始（重新出生/重新装填/重新进入姿态），不得"连着录一大段再切分"，除非该项方法明确规定（如射速用单次连射内多发间隔）。
- 统计量：
  - **中位数**（主值）、**极差**（max − min）、样本数 n、最小/最大。
  - **帧时间不确定度**：每个时间值 ±1 帧（`±1/fps`）。最终不确定度 = `max(极差/2, 1 帧)`。
  - 比值/速度类：按误差传播计算（速度 `v = d / t`：`δv/v ≈ sqrt((δd/d)² + (δt/t)²)`）。
- **离群值**：只允许剔除"操作失误"（如装填被打断、误按键），并在记录里注明原因；不得因"偏离预期"剔除。
- **置信度等级**见 §4.0。若极差 > 中位数的 20%，置信度降一级，并说明可能原因（如服务器 tick、随机散布）。
- **服务器 tick 量化提示**：多人游戏服务器按固定 tick 处理，某些时序（如射速）在录像中会呈现为"量化后的间隔"。测量射速应用**长连射的平均间隔**，而非单个间隔。

## 3. 分析方法

### 3.1 工具栈（均免费/开源）

| 用途 | 工具 | 备注 |
|---|---|---|
| 抽帧/转封装/裁剪/音频提取 | **ffmpeg / ffprobe** | 命令行；自动化分析的基础 |
| 逐帧播放 | **mpv**（`.` 前进 1 帧、`,` 后退 1 帧；OSD 可显示帧号）；VLC 亦可（`e` 逐帧，精度略差）；**Avidemux** 可精确到帧；**Shotcut**（开源）可作帧级剪辑 | 首选 mpv |
| 波形/频谱 | **Audacity**（开源） | 音频法 §3.3 |
| 图像/像素测量 | **GIMP** 或 **ImageJ/Fiji**（开源，带标定与测量功能） | 像素标定 §3.4 |
| 脚本分析 | **Python 3 + OpenCV + NumPy + SciPy + matplotlib** | 清晰度、光流、模板匹配、峰值检测 |
| 表格/统计 | 任意；推荐直接 Python（pandas）输出 CSV | |

> 分析脚本放 `/tools/ref-analysis/`（建议路径，待任务文件创建；见 §9）。脚本只读取录像/抽帧，不得联网上传录像。

### 3.2 逐帧读时序（基础法）

方法码 **M-FRM**：

1. `ffprobe` 确认恒定帧率与分辨率。
2. 用 mpv 逐帧定位**事件 A 的首帧**（如枪口火光首帧）和**事件 B 的首帧**，记录帧号。
3. `Δt = (nB − nA) / fps`，不确定度 ±1 帧。
4. 多个事件（如 N 发连射）取首尾 `(N−1)` 个间隔的平均以降低不确定度。

抽帧命令示例（给执行者的参考，不是仓库代码）：

```
# 抽取全部帧为 PNG（先裁剪到感兴趣区域以减小体积）
ffmpeg -i in.mkv -vf "crop=W:H:X:Y" -vsync 0 frames/%06d.png
# 只抽 [t0, t1] 区间
ffmpeg -ss T0 -to T1 -i in.mkv -vsync 0 frames/%06d.png
```

> 注意：`-vsync 0`（或 `-fps_mode passthrough`）保证帧不被复制/丢弃；抽帧后张数应等于 `帧率 × 时长`。

### 3.3 音频波形法测射速（M-AUD）

适用于自动武器射速（实际射速）与部分时序（如枪响与击发的相对时间）。**优点**：音频采样率 48 kHz，时间分辨率远高于视频帧。**前提**：枪声每发有明显瞬态，且游戏音频不被其他声音掩盖。

步骤：

1. 在 S-RANGE（或练习场）中录一段**长连射**（≥ 30 发，或打空一个弹匣）。关闭背景音乐，尽量没有其他声音。录制时游戏音频单独一轨。
2. 用 ffmpeg 提取音频：`ffmpeg -i in.mkv -vn -ac 1 -ar 48000 audio.wav`（单声道，仅内部分析用，**不入库、不分发**）。
3. 在 Audacity 里放大波形，或用脚本做**峰值检测**：对 `|x(t)|` 做包络（如 1 ms 窗口 RMS），在包络上找峰，峰间最小间隔设为预期间隔的 50%，去除回声/混响的次峰。
4. 取第 1 发到第 N 发的峰时刻 `t1…tN`，射速 `RPM = 60 × (N − 1) / (tN − t1)`。
5. 同一武器重复 ≥ 5 次连射，取中位数与极差。
6. **交叉校验**：同一段视频用 M-FRM 数枪口火光首帧，两种方法结果应在 ±2% 内（视频帧量化误差在长连射中被摊薄）。差异大时检查是否有丢帧。
7. **注意项**：
   - 若游戏为"听觉时延"（声音按距离延迟），**在近距离（≤ 5 m）录制**以忽略传播延迟。
   - 多人游戏中声音触发可能与服务器 tick 同步，间隔呈量化；用平均间隔。
   - 若武器有"首发不同音"，首发可排除后再统计。
8. 记录：峰数 N、起止时刻、RPM、使用的峰检测参数（窗口长度、阈值）。

### 3.4 屏幕像素标定法（距离 / 速度 / 下坠）（M-CAL）

目的：把屏幕像素换算成"游戏内米"。**只使用游戏对玩家可见的参考**。

可用参照（按可靠性排序）：

1. **地图网格**：战术地图上的网格（每格代表一个固定距离，格宽从 UI 或官方公开资料读取）。用两个已知网格交点之间的**地面直线距离**。通过"人物沿直线走/车沿直线开，经过两个网格线"的方式测量速度。
2. **指南针刻度**：指南针上的度数刻度可用来标定**水平角度**（§3.5）。
3. **已知尺寸物体**：必须先用可靠来源确定尺寸。例如史实尺寸明确的车辆（官方/博物馆公开尺寸，如车长），或先用网格测得再作为二次参照。**若物体在游戏中的缩放与史实不一致，不得用史实尺寸**；用网格实测。
4. **距离读数 UI**：若游戏在瞄准/测距时有数字读数（如测距仪、炮兵瞄准 UI），可用作交叉校验，但**其本身需要被网格验证**。

方法 **M-CAL-D（地面距离）**：

1. 选择垂直俯视角度（或接近俯视，视觉倾斜小）的地图界面；或使用第一人称下，目标位于水平地面，用**透视校正**。
2. 对第一人称画面，**不要直接用像素量距离**（透视强烈）。改用：**测量时间 + 已知起止点（网格交点）** 得速度（`v = d_grid / Δt`）。起止点通过"角色身体穿过某明显地物"来定帧。
3. 起止点距离 `d_grid` 至少 ≥ 100 m，使 ±1 帧误差占比 ≤ 1%（如 5 m/s 走 100 m ≈ 20 s，±8 ms 可忽略）。

方法 **M-CAL-F（弹道下坠，100/200/300 m 落点）**：

1. 在 S-RANGE 放置带**垂直刻度**的靶标（如已知高度的墙/门/建筑）；或使用同一远处靶标 + 多次射击统计弹着点。
2. 用**固定瞄准基准**（准星/瞄具中心）对准靶标目标点射击；记录弹孔/弹着点（若有可见弹孔或尘土）相对目标点的垂直偏移（像素），经 §3.5 的角度标定转为**角度偏差**，再乘距离得米：`drop_m ≈ tan(θ) × d`。
3. 若游戏没有可见弹孔，用**曳光/尘土/命中反馈**判定，或用"调整瞄准点直到命中固定小目标"的方法二分求出所需**瞄准抬高**（单位 mil/度或像素）。
4. 弹头速度反推：用**曳光弹飞行时间**（枪口火光首帧 → 命中靶标首帧）在 100/200/300 m 的值，`v ≈ d / t_flight`（需 ±1 帧不确定度分析，近距离不确定度大；用 ≥ 200 m 的数据）。
5. 标注：服务器可能做**命中即时判定**（hitscan 或延迟补偿）导致可见弹丸与命中不一致；记录观察到的行为（是否可见弹丸、命中反馈时间）。

### 3.5 角度测量（FOV 与转动标定）（M-ANG）

- **水平 FOV 标定**：
  1. 找到已知水平角度间隔的参照，如指南针刻度（10°/15° 一格）。
  2. 站在固定位置，原地转身，使指南针指向 θ₁ 与 θ₂（如相差 90°），在两帧中读取同一远处参考点的屏幕 x 像素位置 `x1`、`x2`。
  3. 像素/度 的关系在画面中心近似线性：`px_per_deg ≈ (x2 − x1) / Δθ`（Δθ 小到 ≤ 20° 以减小透视误差）。
  4. 水平 FOV ≈ `2 × atan( (W/2) / f )`，其中 `f = (W/2) / tan(FOV/2)`；可用多组 `(x, θ)` 拟合 `x = f · tan(θ − θ0) + W/2` 求 `f` 与 FOV。把拟合结果与游戏内 FOV 设置值对照。
  5. **ADS（开镜）后的 FOV 或放大倍率**：同样方法，在开镜状态下重做；"放大倍率"= `FOV_hip / FOV_ads`（几何近似）。
- **后坐角度位移**：每发后坐把准星在屏幕上移动 `Δy` 像素，用 `px_per_deg` 转为度：`recoil_deg = Δy / px_per_deg`；游戏常用 mil（`1° ≈ 17.45 mil`），记录时给出度，换算由 /data 决定。
- **转动速率**：需要匀速转动的测量，用鼠标固定拖动距离（如 DPI 与游戏灵敏度固定，鼠标拖过桌面标尺 X cm）→ 转了多少度（读指南针），建立"鼠标 cm → 度"的映射，供探身角度、准星晃动等测量做参考。
- **姿态/探身角度**：用地平线倾斜角（图像中线与水平线夹角），用 OpenCV 拟合直线或 Hough 变换求角度；或用已知垂直建筑边缘。

### 3.6 位移/速度的自动提取（模板匹配）

- 在第一人称视频中，对**固定地物**（树、建筑棱边）做模板匹配，得其屏幕位移。结合 §3.5 的 px/度，可得**视角角位移**（后坐、晃动）。
- 对**第三方观察视角**（观战/回放，若有公开视频）可用模板匹配对车辆做**像素速度**，再用 §3.4 转为米/秒。
- 输出：每帧 `(frame, dx_px, dy_px)` CSV，再积分/求导。

### 3.7 主观效果量化：压制模糊与画面抖动（M-IMG、M-FLOW）

压制（suppression）的视觉效果（模糊、变暗、去饱和、镜头抖动、视野收窄）要变成**随时间变化的曲线**，才能与我方实现对比。

**A. 清晰度曲线（M-IMG）：Laplacian 方差**

1. 取画面中心区域 ROI（如中心 50% 宽高；若有准星/HUD 遮挡，用掩膜去除 HUD 区）。
2. 每帧转灰度，计算 Laplacian（OpenCV `cv2.Laplacian(gray, cv2.CV_64F)`）的**方差**，得 `sharp(t)`。
3. 归一化：`sharp_norm(t) = sharp(t) / median(sharp(t_base))`，其中 `t_base` 为压制发生前 ≥ 2 s 的基线。
4. **注意**：场景内容变化会改变 Laplacian 方差。**必须保证镜头静止**（固定视角、站立不动、不开火、不瞄准），且场景光照/内容固定；基线用同一视角未被压制时录制。
5. 输出曲线要点：**起始延迟**（压制触发到 `sharp_norm` 降到 90% 的时间）、**峰值模糊**（`sharp_norm` 最小值）、**恢复时间**（回到 90% 基线所需时间）。均带 ±1 帧不确定度。

**B. 画面抖动幅度（M-FLOW）：光流**

1. 对固定视角下的相邻帧做稠密光流（`cv2.calcOpticalFlowFarneback`）或特征点跟踪。
2. 取画面**背景区域**（排除移动的角色/UI）光流的**中位数**（全局平移）作为每帧的"镜头位移" `(dx, dy)`；幅度 `a(t) = hypot(dx, dy)`。
3. 抖动强度指标：滑窗（如 100 ms）内 `a(t)` 的 RMS，或位移序列的**峰峰值**，再用 §3.5 换算为度。
4. 输出：起始延迟、峰值幅度、频率（对位移序列做 FFT 取主频）、衰减时间。

**C. 其它视觉通道**：

- **暗角/视野收窄**：在中心与边缘取 ROI，比较**平均亮度比** `L_edge / L_center` 随时间变化。
- **去饱和**：HSV 的 S 通道均值随时间变化。
- **颜色/对比度滤镜**：直方图统计。
- 以上都只导出**曲线数字**（采样表），不存截图；曲线可以简化为"分段线性参数"（起点值、峰值、保持时间、衰减时间）写入记录。

**D. 压制触发与累积**：
 通过"在固定位置被固定类型武器压制（第二账号射击）"并改变**子弹擦过的最近距离/数量/距离**，观测上述视觉强度曲线的峰值与速率，从而反推触发半径、累积速率。若游戏不暴露内部数值，只记录观测到的**视觉强度**，并在 `/data` 里用"视觉强度 → 参数"映射。

## 5. 公开资料交叉验证

### 5.1 目的与原则

自测成本高；很多**规则性事实**（如"冷却 X 秒""最大人数 N"）在官方或社区资料里已有。交叉验证用来：（a）降低测量工作量；（b）发现自测错误；（c）判断版本变化导致的差异。

**只记录数值事实，不复制文字**：

- 只把"事实（数字 + 单位 + 版本）"写入 §8 记录，不复制原文句子、不复制表格排版、不抄 wiki 文字，不抄官方更新日志的行文。
- 每条事实附 `来源类型`、`来源 URL`、`访问日期`、`来源版本/日期`（链接必须真实有效；**不得编造链接**）。
- 若来源本身是"数据挖掘"产物（来源不明、疑似拆包得到），**不采信、不记录**（§1.2）。

### 5.2 可查询的资料类型（需要查什么）

| 资料类型 | 可查到的典型信息 | 备注 |
|---|---|---|
| 官方更新日志 / 补丁说明（Patch Notes） | 数值调整（如"某武器射速/弹量/冷却改为 X"）、新增机制、修正 | 对"版本"最有权威；带日期 → 可确定自测应用的版本 |
| 官方开发日志 / 开发者博客 / 开发者访谈（公开视频） | 设计意图（如"压制的目的"）、机制说明、偶有具体数值 | 可用于理解规则；数值以自测为准 |
| 官方游戏手册 / 加载提示 / 教程文字 | 基本规则、操作方式 | 仅作规则核对 |
| 官方商店页面、官方 FAQ | 人数、模式、地图名称 | |
| 玩家社区公开文档（wiki、Steam 指南、Discord 公开 FAQ、论坛置顶帖） | 武器参数表、载具参数、建造成本、占点规则、冷却 | 社区数据可能过时或来源不明；必须标注"版本/日期"与"可靠度" |
| 公开视频（开发者演示、玩家高质量测试视频） | 可逐帧复核的时序（如开镜时间） | 视频本身遵循 §1.3：仅用于读取数字 |
| 第三方公开评测/指南文章 | 手感描述、参考值 | 可靠度最低；仅作"线索" |

### 5.3 冲突优先级

当同一项出现多个来源且数值冲突：

1. **自测（同版本、n ≥ 5、方法交叉验证）** 最高。
2. **官方更新日志/开发日志**（带日期的明确陈述）次之。
3. **社区公开文档** 最低。

处理规则：

- 自测与官方日志冲突：先检查**版本是否一致**、**测量方法是否有偏差**（如 tick 量化、帧率不稳）；确认无误后以自测为准，并在记录的"备注"列写明冲突与可能原因。
- 官方日志与社区文档冲突：以官方为准，社区文档标记为"待更新"。
- 只有社区文档、无自测：置信度最高 `C`，并在 `/data` 里作为"初值 + 待调参"。
- 同来源不同版本：**绝不混用**；按版本分别记录。

### 5.4 查证记录格式

在 `measurements/{ID}.md`（§8）里增加 "公开资料" 小节，每条一行：

```
- 事实：<数字+单位>（版本/日期：…）；来源类型：官方日志/开发日志/社区文档；URL：…；访问日期：YYYY-MM-DD；与自测关系：一致/冲突/无自测
```

## 6. 史实基线

### 6.1 取舍规则（先读）

| 属性类别 | 以谁为准 | 说明 |
|---|---|---|
| 外形、口径、弹种名称、弹匣/弹夹**容量**、武器重量、全长、枪管长 | **史实** | 以博物馆/手册为准 |
| 理论射速（周期射速）、枪口初速、有效射程 | **史实**为第一来源 | 作为 `/data` 初值；在游戏性里允许有限度偏离，须在数据里注释 `deviation_reason` |
| 栓动循环/射击节奏的**实际手感时序**（开镜、切枪、换弹动画时长、后坐、扩散、晃动、移动速度、体力） | **对标测量** | 无史实对应，或史实与游戏节奏无关 |
| 伤害、致死发数、冷却、资源 | **对标测量 + 平衡** | 游戏性数值，按 §7 调参 |
| 装填动作的**物理上限**（如 M1 Garand 8 发一夹） | **史实** | 容量决定；耗时按对标 |
| 载具：最高速度/战斗全重/火炮口径/弹种 | **史实**为初值；游戏节奏（加速曲线、转向速率、装填时间）**以对标为准**，偏离史实需注释 | 防止"过于拟真但不好玩" |

冲突处理：

1. 史实值与对标测量值冲突且属于"外形/口径/弹容量/射速"：**以史实为准**，在 `/data` 记 `source: "historical"`。
2. 属于"手感类时序"：**以对标为准**，在 `/data` 记 `source: "ref_measurement"` 并引用本文件的 ID。
3. 都不属于或存在争议：由人负责人裁决（见 §9），默认以"可玩性优先、可解释"为原则。
4. 任何偏离史实的数值必须写 `deviation_reason`（如"为平衡下调射速"）。

> **关于"公共领域"的说明**：美军 1940 年代技术手册作为美国联邦政府作品，通常被视为公有领域，但**各网站的转录/扫描版本可能带有站点编辑版权或有错误**，且德军材料与出版物版权状况不同。本文档**未做法律审查**；以"只提取数值事实、不复制整段文字、不上传原件"为纪律。要把任何原文复制进仓库前须由人负责人确认（见 §9）。

### 6.3 需要在 `/data` 里登记的史实字段（建议）

每把武器在 `weapons/{w}.json` 里分三个来源标记的字段组：

- `historical`：`caliber`、`cartridge`、`mag_capacity`、`cyclic_rpm`、`muzzle_velocity_mps`、`mass_kg`、`length_mm`、`source_refs[]`（来源 ID，含页码）
- `ref_measurement`：由 §4 填入的手感类字段（附 ID 与版本）
- `gameplay`：最终采用值、`deviation_reason`、`tuning_status`（`initial` / `calibrated` / `locked`）

### 6.4 史实与对标冲突时的示例（假设性说明，不含真实数值）

- 若对标作品的某武器**射速**与史实周期射速差异明显：外形与弹容量用史实；`gameplay.rpm` 默认取史实周期射速；若对标的游戏节奏要求偏离，则在 `deviation_reason` 注明并保留 `historical.cyclic_rpm` 不改。
- 若对标的**开镜时间**无史实对应：直接取对标测量中位数（经 §7 调参）。

## 7. 调参工作流

### 7.1 总流程

```
[1 采集参考作品录像]  →  [2 逐帧/音频/像素分析]  →  [3 记录 measurements/{ID}.md + summary.csv]
        │                                                        │
        │                                                        ▼
        │                                         [4 映射到 /data 字段（拟议路径见 §4）]
        │                                                        │
        ▼                                                        ▼
[8 版本更新→旧数据 stale]                     [5 在我方游戏中用同一套方法复测]
                                                                 │
                                                                 ▼
                                               [6 误差对比（容限 §7.3）→ 调整 /data]
                                                                 │
                                                                 ▼
                                            [7 自动化回归：headless 测试断言（§7.4）]
```

### 7.2 映射规则

1. 每个 `/data` 的游戏性字段旁注：`source: ref_measurement`、`ref_id: W-07`、`ref_version: <构建号>`、`ref_median: <值>`（数字来自记录）。
2. 一个测量项可能影响多个字段（如 W-01 射速 → `fire.rpm` 与 `fire.interval_ticks`）；换算规则写在 `/data` schema 文档，**不得散落在代码**。
3. 服务器 30 Hz 模拟（见总纲）：时序被量化为 tick（≈ 33.3 ms）。映射时先取"目标时序 → 最近的 tick 数"，再检查量化误差是否在容限内；射速等小间隔需要用**累加器/分数 tick** 以避免系统性偏差（实现细节在 sim 任务里，此处只提醒测量侧要用长连射平均验证）。
4. 客户端表现层的时序（动画、UI、特效）以 60 fps 渲染为基线；允许动画时长非 tick 整数倍。

### 7.3 误差容限

| 类别 | 容限（我方复测值 vs 目标值） | 备注 |
|---|---|---|
| 时序（射速、换弹、开镜、切枪、装填、冷却、UI 停留） | **±5%** 或 **±1 帧@60 fps（±16.7 ms）**，取**较大者** | 目标值 < 0.3 s 时按"±1 帧@60 fps"；目标值 ≥ 1 s 时按 ±5% |
| 速度（移动、载具） | ±3% | 由距离/时间合成；距离 ≥ 100 m 以降低不确定度 |
| 距离/半径/范围（触发、杀伤、可闻） | ±5% 或 ±1 m（取较大者） | 可闻距离受混响/遮挡影响，容限放宽到 ±10%，须在记录里说明 |
| 角度（后坐位移、FOV、探身） | ±5% 或 ±0.1°（取较大者） | |
| 统计量（散布 CEP、致死发数、扩散） | 中位数在目标 ±10% 内，且分布形状（95 分位）在 ±15% 内；致死发数必须**精确相等** | 致死发数是离散量 |
| 曲线型（压制视觉强度、体力曲线） | 起始延迟/峰值/恢复时间三个关键点各在 ±10% 内 | 形状（单调性、拐点）用目测 + 差值 RMS 辅助 |
| 对标参考本身的不确定度 | 若参考测量的不确定度 > 容限，则容限放宽到参考不确定度，并降低置信度 | 避免过拟合噪声 |

> **不追求"复制"**：容限是"与对标测量值接近"的判据；若游戏性需要偏离，须在 `/data` 注明 `deviation_reason`，并在 §4 对应行备注。

### 7.4 同法复测（我方游戏）

- 我方游戏提供**测量模式/调试场景**（后续任务）：固定练习场、网格叠加、可调时钟、可导出事件日志。**我方游戏可以导出内部日志**（它是我方的）；但为了与对标可比，**必须同时用录像分析法复测**，两者互相校验——这样既验证了方法，也发现渲染延迟、动画不同步等"手感差异"。
- 复测使用与 §2 相同设置（≥ 120 fps 录制、关闭动态模糊、固定 FOV）、相同场景编号与重复次数。
- 复测结果记在同一个记录文件的 "我方复测" 小节，列与参考列并排，输出误差百分比与是否通过。

### 7.5 自动化回归（headless）

目标：一旦某项通过验收，**锁定数值**，防止后续改动无意中破坏手感。

- 每个已校准的 `/data` 字段在 Rust `sim` 的测试里有一条**断言**（或在 `headless-client` 的场景测试里）：
  - 例如"以 `weapons/{w}.json` 的射速在 N tick 内发射的发数 = 期望发数 ± 容限"、"从按下开镜到 ADS 稳定的 tick 数 × 33.3 ms 与目标时序差 ≤ 容限"、"站立冲刺 N 秒后体力耗尽"。
- 测试读取 `/data` 里 `ref_median` 与容限字段，**不得把参考数字硬编码进测试**。
- 表现层（动画/UI/视觉效果）的时序用 Playwright 固定机位 + 事件时间戳断言（`performance.now()` 差值），容限同 §7.3。
- 回归在 CI 中运行；任一断言失败须在 PR 里说明"是有意调参还是回归"，有意调参必须同步更新 `ref_*` 或 `deviation_reason`。
- 调参状态机：`initial`（来自史实/估计）→ `calibrated`（已对标且通过 §7.3）→ `locked`（已有回归断言）。

### 7.6 版本漂移处理

- 参考作品更新后（读官方日志发现数值变化）：相关项标记 `stale`；**是否跟随**由人负责人/设计决策（默认不盲目跟随，仅在我方设计目标需要时重测）。
- 我方 `/data` 改动不自动触发重测，但改动 PR 须注明是否影响某个已 `locked` 项。

### 9.2 人类负责人行动项（要写入 NEEDS_HUMAN）

下列事项**只能由人完成**（或需要人决策/授权）。请汇总写入 `NEEDS_HUMAN`：

1. **合法获取并安装参考作品**，并通读其用户协议/EULA，**确认允许录制与内部分析**；若有限制，须决定如何调整（如只用公开视频）。（M0 前）
2. **准备录制设备**：能稳定输出 ≥ 120 fps（目标 240 fps）1080p 的 PC/显卡与存储（原始录像体积大，估算需数百 GB，**未核实具体用量**，随测量量增长）；若硬件不足，决定降配或租用。
3. **人工游玩录制**：按 §2、§4 在练习场/空服/私人服务器录像；每项重复 ≥ 5 次。**M0 批至少需要 2 到 3 个录像会话**（步枪与移动），人负责人或指定测试员进行。
4. **第二账号 / 协助者**：S-DUMMY、S-AUDIO、占点人数（R-01）、救起（H-09）、压制（U-01–U-11）、手雷杀伤（G-08）等需要至少 1 个协助者；R-01 的多人规律需要 5–10 人场景（可用公开视频，或组织测试局）。
5. **私有存储与访问控制**：指定录像存放位置、访问人员、保留期限（§1.3），并确认**录像不会被提交、不会上传到任何公共服务**；确认 `.gitignore` 与 CI 排除规则。
6. **版本与日期记录**：每次录像前后记录参考作品构建号；游戏自动更新应关闭或记录更新时间点。
7. **裁决规则**：对 §6.1 中"争议"项的取舍；对"对标值与史实值严重冲突"的项做决策。
8. **来源合法性确认**：德军条令（HDv/Merkblatt）、Hogg 等出版物、博物馆资料的获取与使用边界；是否可把转录文本放入仓库（默认：不放，只存数值事实）。
9. **仓库路径确认**：`docs/measurements/`（记录）与 `/tools/ref-analysis/`（分析脚本）；`.gitignore` 增加 `docs/measurements/raw/`、`assets/incoming/ref-captures/`。
10. **工具安装**：执行者运行环境需安装 ffmpeg、Python 3 + OpenCV/NumPy/SciPy、Audacity、mpv（均免费开源）；若执行者在云端容器中无法访问录像（私有存储），需决定传输方式（**不得上传到不受控的第三方**）。
11. **分析人员**：确认由 AI 执行者做逐帧分析；人负责人对 §4 的"置信度 A"项抽样复核（建议每批至少 10%）。
12. **对外沟通**：在公开测试或文档里**不得出现参考作品名称/截图**；确认对外文案审查人。
